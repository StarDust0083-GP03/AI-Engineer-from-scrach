多智能体如何协作

调度分析、维修检查与报告汇总可以分工，但它们必须引用同一批快照、遵守同一份任务契约。多 Agent 的重点在交接、状态和失败隔离。

多 Agent 不是目的

早班报告需要读取站点缺口、核对停运车辆并提出运输建议。若一个 Agent 已能在短上下文里完成，拆成多个角色未必有收益。只有当维修规程与调度数据的上下文互相干扰、权限不同，或独立读取可以并行时，拆分才解决具体问题。

可以让库存分析角色只读站点状态，维修角色只读工单与规程，汇总角色只接收经过验证的结构化结果。这样汇总不必看到完整维修记录，也不能直接修改工单。但新增角色后，快照时间是否一致、缺字段怎样拒收、失败由谁恢复，都成为必须处理的协议问题。

多个角色也可能同意同一个错误。若全员读取了同一份过时快照，投票并不能让它更新。共享模型与共享数据会造成相关失误，需要外部证据和独立校验，而非只增加发言次数。

本章用合成站点任务说明并发与协作，不运行真实调度平台。端到端收益应比较相同任务的正确率、总费用和完成时间。[2] 角色更多、流程更长都不能作为质量提升的证据。

协作模式与通信模式

协作拓扑与通信载体是两个维度。一个主管分工流程既可读共享黑板，也可通过队列交付任务；不要把队列误认为一种推理策略。

上下文切分

交接应该选择下游真正需要的字段。库存分析角色输出站点 ID、可调量、快照时间和证据编号，维修角色输出停运车辆集合和相关条款。汇总者需要的是这些结果，不是两份完整对话。

字符截断只能限制大小，无法保证语义完整。若截在“不得投入”中间，下游甚至可能读到反方向结论。下面用字段投影来控制边界，并为缺失字段报错。

教学代码，可离线检查；不连接业务服务
def handoff_stock(raw):
    required = {"station_id", "movable", "snapshot", "source"}
    missing = required - raw.keys()
    if missing:
        raise ValueError(f"交接缺字段：{sorted(missing)}")
    return {key: raw[key] for key in sorted(required)}
out = handoff_stock({"station_id":"LC-02", "movable":8,
                     "snapshot":"s-0730", "source":"inventory-fixture",
                     "full_dialogue":"下游不需要这段内部对话"})
assert "full_dialogue" not in out and out["movable"] == 8

上下文是否膨胀取决于传递结构。每一步只传前一步结果时，不会天然指数增长；不断携带所有角色完整历史才容易快速增大。记录每步输入字节数和 token 用量，才能判断切分是否真的减少了成本。

黑板、订阅与队列

黑板提供共享状态位置，发布订阅传达事件，队列分配待处理工作。内存版可以演示接口，但没有自动获得跨进程持久性、投递保证或事务隔离。

共享字典加锁能保护一次读写，却不一定保护先读再算再写的组合。库存角色与维修角色同时更新同一份运行状态时，需要版本比较或单写者策略。下面演示最小的比较并交换。

进程内教学黑板，不提供跨进程持久化
from threading import Lock
class Board:
    def __init__(self):
        self.lock = Lock()
        self.values = {}
    def put(self, key, expected_version, value):
        with self.lock:
            current = self.values.get(key, (0, None))
            if current[0] != expected_version:
                raise ValueError("version_conflict")
            self.values[key] = (current[0] + 1, value)
            return current[0] + 1

board = Board()
assert board.put("stock", 0, {"LC-02":8}) == 1

发布事件若先于结果落盘，消费者可能收到完成通知却读不到内容。更可靠的顺序是先持久化结果，再发布带结果 ID 的事件，并通过幂等消费处理重投。消息队列确认过早会在 worker 崩溃后丢任务，确认太晚则可能重复投递。

Redis、RabbitMQ 和 Kafka 并非可无差别替换的名字。它们的顺序、消费模型和保留策略不同，应用应先明确是否需要至少一次投递、任务认领或事件日志，再选择基础设施。

阶段状态机

阶段状态机约束什么时候允许交付。对于建议生成，INIT 读契约，PLAN 分解，EXEC 收集证据，VERIFY 检查一致性，DONE 只表示已验证建议。实际工单执行需要另外的审批和回执状态。

教学代码，可离线检查；不连接业务服务
ALLOWED = {"INIT":{"PLAN"}, "PLAN":{"EXEC"}, "EXEC":{"VERIFY"},
           "VERIFY":{"EXEC","DONE"}, "DONE":set()}
def transition(state, next_phase):
    if next_phase not in ALLOWED[state["phase"]]:
        raise ValueError("illegal_phase")
    if next_phase == "DONE" and not state.get("verified"):
        raise ValueError("verification_required")
    return {**state, "phase":next_phase, "version":state["version"] + 1}
s = transition({"phase":"VERIFY", "version":4, "verified":True}, "DONE")
assert s["version"] == 5

允许 VERIFY 回到 EXEC 还不够，必须携带哪项失败、哪些结果失效，以及重试预算。否则库存查询成功也会被反复重跑。持久化快照应包含阶段、产物 ID、版本和未完成动作，重启后先核对外部回执，不能仅恢复一个字符串阶段就重放所有副作用。

图与角色两种编排

图编排用边表示依赖与条件，角色编排用职责和任务分配描述工作。两者可以同时出现：维修角色是图中的一个节点，审核节点根据结果决定回到维修还是结束。

原项目的极简 SimpleGraph 只沿第一条后继边前进，并不因此拥有真实框架的并行、条件路由和检查点。下面先以可检查的依赖集合表示图。

教学代码，可离线检查；不连接业务服务
needs = {"stock":set(), "maintenance":set(),
         "proposal":{"stock","maintenance"}, "verify":{"proposal"}}
def ready(done):
    return sorted(task for task, deps in needs.items()
                  if task not in done and deps <= done)
assert ready(set()) == ["maintenance", "stock"]
assert ready({"stock","maintenance"}) == ["proposal"]

角色模型给出谁有权接收什么任务，但不应靠角色提示词模拟授权。执行器仍要检查其工具权限。

教学代码，可离线检查；不连接业务服务
roles = {
    "inventory": {"tools":{"read_station"}, "produces":"stock_snapshot"},
    "repair": {"tools":{"read_order","search_manual"}, "produces":"repair_check"},
    "writer": {"tools":set(), "produces":"proposal_text"},
}
def may_call(role, tool):
    return tool in roles[role]["tools"]
assert not may_call("writer", "read_order")

角色描述影响模型行为，边控制步骤顺序，权限表约束真正执行能力，三者不应混成一段长提示。联合讨论适合比较已有证据，不适合无止境轮流复述。若连续两轮没有新增证据，应请求外部数据或停止，而不是让所有角色再表态一次。

任务路由

路由需同时考虑能力、权限和负载。空闲的汇总角色没有维修读取权限，就不能因为负载低而接维修任务。若没有可用角色，任务进入等待或人工处理，这是正常的显式状态。

片段：capacity 必须在配置加载时验证为正数
def pick_worker(workers, skill, tenant):
    candidates = [w for w in workers if skill in w["skills"]
                  and tenant in w["tenants"] and w["load"] < w["capacity"]]
    if not candidates:
        return {"status":"pending", "worker":None}
    winner = min(candidates, key=lambda w:(w["load"]/w["capacity"], w["id"]))
    return {"status":"assigned", "worker":winner["id"]}

按容量归一的负载比单纯任务数更能反映异构 worker，但任务时长差异大时仍会失真。认领应原子增加负载并附租约，超时后才能重派；若选择与认领分开，多个调度器可能同时把任务派给看似空闲的同一角色。生产还要考虑优先级和饥饿问题。

冲突解决

库存角色建议搬 8 辆，维修角色指出其中 2 辆有制动故障。这个冲突应回查车辆集合与快照，不应靠多数票决定是否忽略维修证据。硬约束优先于偏好。

对两条都合法的路线，才可以比较预计时间、满足缺口和风险。分数也要有计算依据，不能让角色自报一个高信心就获胜。

教学代码，可离线检查；不连接业务服务
def arbitrate(proposals):
    legal = [p for p in proposals if not p["violations"]]
    if not legal:
        return {"status":"needs_revision"}
    best = min(legal, key=lambda p:(p["unfilled"], p["minutes"], p["id"]))
    return {"status":"selected", "id":best["id"]}
assert arbitrate([{"id":"fast", "violations":["brake_fault"],
                   "unfilled":0,"minutes":10}])["status"] == "needs_revision"

即使三个角色支持同一方案，也要看它们是否引用独立证据。[1] 共享一份错标车辆状态的表，会让投票重复计算同一个错误来源。需要不同数据源或确定校验，而非简单随机改写角色身份。对证据确实冲突且无法复核的情况，应保留分歧交给值班负责人。

刹车与可观测

多角色运行的停止条件不应依赖任一文本里出现 DONE。应检查结构化任务状态、必需产物与验证回执，并同时限制轮次、总时长、费用和无进展次数。重复动作检测也应以动作类型、归一参数和状态版本构造指纹。

简单指纹片段：嵌套参数应使用规范 JSON，而非直接 tuple
def repeat_guard(actions):
    seen = set()
    for action in actions:
        key = (action["tool"], tuple(sorted(action["args"].items())), action["version"])
        if key in seen:
            return "repeated_without_new_state"
        seen.add(key)
    return "ok"
assert repeat_guard([{"tool":"read_station","args":{"id":"QH-07"},"version":1}]*2) != "ok"

同一读取在状态改变后再次执行可能有意义，所以版本也参与判断。反过来，每次修改一点措辞都能躲过文本去重，无进展检测应看新增证据、未满足约束和产物变化。

Trace 记录父子任务、角色、快照 ID、开始结束、状态和实际 usage。字符数除以 4 只是粗估，对中文、工具 Schema 和长结果可能误差很大。看端到端瓶颈时，还要记录队列等待与协调耗时，而非只累计模型推理时间。权限拒绝和验证失败也应成为事件，不要只记录成功调用。

框架实战

框架能减少状态和消息样板，但不会替你定义正确交接。选择框架前，可用三项固定产物验收：库存快照、维修阻断列表和包含剩余缺口的建议。让某个 worker 超时，确认汇总不会生成全量完成声明。

框架方向适合的表达本案例要补的业务边界
AutoGen 对话与调度角色轮转、选择参与者何时停止讨论、哪些输出可交付
CrewAI 角色任务职责与任务产物权限在执行器检查，不只靠人设
LangGraph 状态图条件边、状态与恢复验证失败返回哪个节点、旧结果怎样失效

仓库的分层示例将 Worker、Orchestrator 和 Supervisor 分开。自行车场景可以让 worker 读取，编排者管理依赖，监督者核对库存和维修版本。监督者若只读编排者摘要而不看关键证据，就无法独立发现汇总遗漏。

人工审批适合创建搬运工单等有副作用动作。审批页面应展示数量、站点、证据和快照年龄，不能只显示一句“是否同意执行”。可观测平台负责保存轨迹和评估结果，告警阈值仍需要业务决定；本页没有运行任何框架的在线示例。

延伸对照：多智能体的研究脉络

多 Agent 研究展示了分工与讨论的可能收益，也记录了协调失败。把研究结果迁移到调度业务时，需要重新定义环境、权限和成功标准。

学术原型

AutoGen 研究可对话角色的组合，CAMEL 使用角色扮演，MetaGPT 用标准工作流程约束交付，Multiagent Debate 探索相互质疑。它们说明不同协作结构值得测量，不能直接证明你增加三个角色就会减少站点调度错误。

本案例可先用单 Agent 加确定校验建立基线，再比较分工是否降低上下文冲突和总耗时。若只改变角色提示而使用同样数据与同样验证，收益可能很小。

失败模式的系统研究

MAST 研究将多 Agent 失败分为规格设计、角色错位以及验证终止等类型。库存未说明可借与可调的区别属于规格问题，维修角色没把故障列表交出去属于交接问题，汇总未验收就停止属于终止问题。先按这些位置定位，比增加讨论轮数更有针对性。

动手验证

先用固定角色输出测试协议，再考虑模型能否稳定生成这些产物。离线测试可以注入失败和重复事件，而不产生调度副作用。

练习一：观察上下文膨胀

给库存、维修和汇总角色各一份合成数据。分别记录传全文、传前 500 字符和传字段投影时的长度及缺失字段。不要预设长度一定指数增长，用实际生成方式解释曲线。特意把“不可调出”放在截断边界后，观察机械截断是否损害安全条件。

练习二：给状态机加一条合法迁移

给 PLAN 增加返回 INIT 的边，表示任务目标已修改。测试返回后旧库存和维修结果是否被标记失效，新目标是否提升版本。只添加一条边但保留旧 verified=True，会让旧验证意外放行，应有断言阻止。

练习三：让刹车更严格

除了重复指纹，再记录连续三轮新增证据数为零时停止。构造每轮措辞不同、但没有新快照的假角色输出，确认它被无进展规则阻止；再插入一个真正的新快照，确认计数重置。短文本不一定没价值，不宜只按字数判停。

练习四：复现一次“假独立”

建立三个投票记录，它们都引用同一个库存快照。再添加一份独立维修回执指出故障。先按票数，再按硬约束处理，比较结论。将来源 ID 纳入日志，让“意见很多但证据只有一份”在运行记录中可见。

回顾与自测

拆分角色以后，信息交接应更明确，权限应更窄，失败应更容易定位。若这些条件没有改善，多 Agent 往往只是增加协调开销。

黑板用了锁，就能保证跨 Agent 一致吗？

锁通常只覆盖本进程的一次操作。复合读改写、跨进程状态和重复任务仍需版本、事务或单写者策略。

多数赞成能覆盖维修阻断吗？

不能。故障车不得搬入可运营集合属于硬条件，应该核查证据或修改方案，而非通过票数取消。

为什么 DONE 文本不是可靠停机条件？

角色可能提前声明或在资料里引用这个词。停止应取决于结构化任务状态和独立验证回执。
