两个前沿方向

海上作业船的工作站白天连接岸站，夜里可能只有间歇网络。工程师希望为助手临时增加一个只读诊断工具，又不希望原始报文被顺手上传。这是两类不同问题：运行时怎样采用新的能力定义，数据与动作在哪里发生。即使模型都在本机，新增工具也可能调用公网。

14-deepseek-harness/ 的材料讨论可配置、可替换的 Harness，15-Edge-Agent/ 讨论端侧闭环。本章把它们用于一个新的教学任务：检查 B17 波高突变，生成本地草稿，在获准后只发送摘要。两个目录的架构讨论不能当作已经交付并经过设备测试的完整产品。

配置化扩大可调整范围，本地化缩小默认数据边界，两者都需要独立的验证层。若助手能修改工具白名单和验证规则，就可能把原先的保护一并改掉；若端侧推理失败自动回退云端，也会改变数据流。部署位置与更新策略都应能被审计。

所有 Harness 共用的循环

一次质检请求可以经历读取、计算和解释多次模型调用。第一步模型请求读取 06:00 至 07:00 的报文，宿主执行后回填观察；第二步模型根据结果请求差值统计；第三步形成草稿。每次模型调用都是一次新的请求，宿主负责发送相应历史与上下文，不能期待模型在未收到记录时自行记得上一步。

材料用 Step 表示一次推进，Turn 表示一条用户输入的完整循环。术语随系统不同，但计账必须明确：上面的教学轨迹有三次模型决策、两次工具执行，不是“整条消息只有一次 API 调用”。本地编排决定何时发出调用，模型与工具各自产生计算或网络开销。

模型能力、工具质量、证据和预算共同影响结果。增加循环次数有时能补齐证据，也可能重复错误查询，不能说只要让环转更久就会更聪明。可用停机条件应包括无需新工具、证据不足、预算耗尽、用户取消以及不可恢复故障，最终报告须区分这些原因。

Coding Agent 的四块

把助手拆为四块，可以为每次决策保存一份配置清单。这样修改工具后，能知道下一步究竟采用了哪个版本。

模型

工具注册表

工具表列出读取报文、计算统计和保存草稿。每个工具都有实际实现、参数约束和权限；仅把一个名字加入 schema 还不具备执行能力。记录工具表版本后，才可解释“为什么上一步没有诊断工具，下一步却能调用”。

Prompt 组装

提示组装把身份、项目约定、工具说明和当前证据组合起来。教学约定“原始报文只读”应同时被工具权限落实。工具变化时提示中的能力清单也需更新，否则模型仍可能请求已移除的名字，或不知道新能力存在。

Session

代码 vs 配置

配置化把模型选择、提示和可用能力从固定分支中外置，宿主在规定的重建边界读取它们。若下一步重新组装 Agent，变更可能在下一步生效；若只在启动时读取，则仍需重载。关键是读配置的实际时机，不是文件扩展名叫 YAML 还是 JSON。

比如把工具表从 V3 改到 V4，增加只读 inspect_flags。应先校验名称、schema、实现位置和权限，再把 V4 发布为当前版本。正在执行的 V3 调用不宜被中途换实现，否则同一个调用的参数和输出可能不再匹配。可采用每个 step 固定一份清单，下一步再原子切换。

代码同样可以动态加载，配置也可能加载可执行插件，所以“代码必须重编译、配置改动零成本”过于绝对。配置需要验证、授权、错误恢复和测试，只是可能省去完整打包部署。将 loop 作为可替换组件时，还需约定事件、队列、工具结果与终止语义，不能仅保持同名入口。

材料中的现场演示记录了中途增添工具的体验，那是来源描述，不是本次实测。复现时应检查下一步的工具清单与实际调用，而非只看模型说“新工具已安装”。

SDK 嵌入与 Web 门户属于不同外壳，均可使用同一配置系统；是否立即生效、是否安全，仍取决于宿主如何加载和验证。配置损坏时应保留上一份有效版本，不能半套新 schema 搭配半套旧实现继续工作。

Tool 与 Skill 不是一回事

Tool 把某项操作暴露为有参数和结果的程序能力，Skill 描述如何组织多步工作。二者可能一起使用：质检技能指导先看缺测、再核对突变，实际数值由读取和计算工具产生。模型自己写出一个数字不等于已经测量。

能力适合的形式结果验收
统计 36 个时槽中 3 个空值有输入校验的计算工具缺测率 3/36≈8.33%，保留分子分母
调查波高异常的步骤可按情况分支的技能候选原因与证据对应，未知项显式保留
外发摘要受审批与目标限制的工具审批、幂等结果及投递状态

工具不一定没有不确定性，远端 API 也会失败；技能也可以有很固定的流程。选择时看需要封装的契约：精确数值、权限和副作用应由程序边界负责，多步判断可由技能组织。不要用技能文字替代发送工具的授权检查。

读取工具应返回单位与时间，计算工具说明是否忽略空值，保存工具返回实际路径。若工具只回“成功”，模型便难以判断处理的是哪批数据。设计良好输出可以减少后续猜测，比把所有操作都变成自由 shell 更容易验证。

能改自己的 Agent

让助手提出运行配置修改，可以缩短能力调整反馈。它发现现有工具无法区分异常码，生成一个新只读工具建议，测试通过后由宿主加载，这是可控扩展。若允许它同时降低测试要求、修改审批白名单并宣告通过，就失去独立验证。

可以把变更分成提案、沙箱验证、授权、激活和回滚五种状态。提案保存修改内容与理由，验证使用固定假报文，激活记录旧新版本；超范围的文件、网络或权限变化转人工。[1] 这里是加固设计，并非材料已经实现的安全机制。

自改写 loop 还会改变轨迹怎样被记录。验证器必须在可改写区域之外，至少能检查工具结果配对、预算终止、取消传播与审计连续性。否则一个新 loop 可能通过不再记录失败来“提高成功率”。学习这个方向时，应先让助手只改无副作用的配置，再逐项扩大范围，不能默认放开所有运行时文件。

端侧 Agent 是什么

端侧 Agent 在数据产生处完成推理、取证和动作。对于船载工作站，原始浮标报文、维护手册和本地草稿都留在同一可信域内，网络断开后仍能生成有边界的质检说明。它与只做一次分类的 Edge AI 不同，因为它还会多步调用工具与维护任务状态。

形态在本地完成的内容剩余依赖
传感器分类器判定单段波形是否可疑上层决定如何处理
云端助手可能只做采集与界面上传上下文、远端模型与工具
端侧助手本地推理、检索和受限工具循环可选授权后的摘要投递

本地化可能降低网络往返与带宽需求，但小设备的推理速度也可能更慢。是否可行要看模型大小、内存带宽、上下文和工具预算，不可仅因使用 NPU 就承诺低延迟。隐私同样需要检查工具、遥测与 fallback，模型权重在本机并不能保证其他组件不联网。

可靠做法是列出数据流：原始报文只供本机读取，派生统计允许本地存储，摘要在批准后外发，日志默认脱敏。离线时不能把旧缓存伪装为最新远端资料，报告应写清观测与资料的有效时间。

端侧运行时与一轮

端侧的一轮任务还要受设备状态影响。内存不足、电源紧张或散热受限时，系统应减少工作或停止，而不是为了完成一段解释让采集服务失去资源。

UI

Agent

Agent 先装配本地相关片段，判断需要的工具，再依据观察继续。教学预算可设最多 4 次决策、最多读取 200 条报文；达到上限就返回当前可证实结论及未完成项。具体电量和温度阈值需设备工程师定义，不能由语言模型临场决定。

本机运行时

本机运行时包含量化模型、检索索引、记忆和设备工具。4-bit 权重可减少存储，但仍需量化元数据、KV 缓存、激活和运行时空间。llama.cpp、MLX、Core ML、QNN、ExecuTorch 面向不同平台和后端，不能统一称为都能直接吃满 NPU。算子支持与落到 CPU 的回退需要实测。

感知小模型可以先给出异常候选，语言模型再组织解释。采集和安全控制应保有独立优先级，不能因语言循环阻塞停止报文接收；本地数据库与文件写入也要处理掉电恢复。

工具门：默认不出域

出域判断应放在能够看到实际目标与载荷的执行边界。模型请求“发给岸站”时，程序应知道具体主机、数据字段、审批和凭据范围，而非只搜索命令文本有没有“upload”。

工具门的教学判定顺序
收到工具请求
  1. 校验工具与参数，拒绝未知能力
  2. 核对设备、路径和目标是否在允许范围
  3. 若有出域，检查当前载荷与目标的显式授权
  4. 若会改变设备或删除数据，进入独立高风险审批
  5. 执行并记录实际结果
拒绝 / 超时 / 取消均不得标为执行成功。

白名单可以只包含报文只读、手册检索、统计和草稿保存。摘要投递是单独能力，限制字段与固定岸站目标；它不授权上传原始波形。DNS、重定向、子进程或外部脚本也可能形成网络路径，严格不出域需要网络策略配合，提示词和工具名称检查不够。

日志、崩溃上报和依赖遥测也应列入数据流检查。用假数据进行断网试验时，可以检查应用是否继续运行、是否尝试云端回退以及用户看到什么失败说明。没有网络测试证据，不能把默认不出域写成已经证明的隐私保证。

安全：可预期比聪明更重要

安全关键动作应与语言解释解耦。助手可以解释候选维护步骤，但不应凭生成文本直接改变浮标采样频率、固件或电源设置。即使操作者同意，工具仍要检查设备允许范围和当前状态。

风险程序控制失败时的可接受行为
把缺测补成真实值区分 observed 与 estimated 字段，发布规则拒绝混写保留空值和缺证据说明
修改设备配置允许值、版本与人工审批拒绝执行，仍可生成只读诊断
资源抢占采集服务内存、时间和进程优先级预算停止语言分析，继续采集
误外发原始记录目标与字段白名单、网络限制本地保存待审摘要

“策略内才动”需要能执行的约束，比如只读挂载、明确路径与字段过滤。语言模型估计自己很有把握并不是放行信号。对于超出支持设备、报文损坏或时间错乱的输入，允许返回无法判断，比在所有输入上硬给结论更符合质检任务。

人工确认也不能替代工程限值。操作者误点批准时，工具仍应拒绝非法采样周期或错误固件型号。所有保护都需要相应反例测试，不能只检查正常操作下没有出错。

学端侧要补什么

学习顺序可以按故障可定位性安排：先用固定假模型跑通循环，再接本地模型；先只读工具，再加出域和高风险动作；最后测整机资源。这样每次增加一个不确定因素，出现故障时更容易知道来自哪里。

岸站工作站的验证顺序
固定回复序列：验证工具结果配对与预算停止
本地推理：验证格式、工具协议与长输入
只读工具：验证路径、设备与空值语义
出域门：用假目标验证拒绝、批准和取消
资源试验：记录内存峰值、热状态与采集延迟
整机验收：断网 / 掉电恢复 / 长时运行

已有云端经验可以复用消息、工具和评测思想，但设备后端的算子与内存行为必须补测；只会运行模型文件也不足以实现受控工具循环。[2] 报告中分别写“纸上预算”“目标设备测量”“待验证项目”，不要用笔记中的理想数值填实测栏。

延伸对照：两个方向的公共背景

插件化与端侧推理都有成熟技术可参考，参考时要把连接能力和安全保证分开。

插件化与可配置架构

插件架构把变化放在稳定接口后面，可替换 loop 则进一步要求一致的事件和状态语义。MCP 统一部分工具连接，不统一所有权限和生命周期；配置中引用插件仍意味着运行代码，必须有来源审查与版本固定。

端侧模型与推理

llama.cpp、MLX 与 ExecuTorch 可作为不同平台的运行时入口。GPTQ 和 AWQ 是量化方法路线，GGUF 是模型文件格式，三者不应当作同一层级的互斥格式。选择时核对模型结构、量化方案、后端支持与设备实测，不能只看文件能否下载。

隐私与端云协同

数据类别默认位置外发条件
原始报文与设备标识本地受控存储本教学方案不开放
派生缺测统计本地草稿去标识、授权与目标核对
错误日志本地轮转脱敏后按维护政策处理
模型上下文本地推理进程云回退必须单独授权

端云协同不等于只能全上传或全不传。字段裁剪、摘要和固定投递目标可以减小数据量，但摘要也可能含敏感信息，需要内容检查和访问控制。

一句话总结

这两个方向最终都要为一次运行给出可核对清单：采用哪版配置、在哪台设备执行、读了什么、改了什么、发到了哪里。没有这份清单，热更新和本地化都很难被验证。

动手验证

以下均为设计练习，无需修改当前工作站配置或连接真实设备。

练习一：区分 Tool 与 Skill

把“计算缺测率”“调查波高突变”“保存草稿”“外发摘要”“更新固件”分类。分别指出程序契约与多步方法所在位置，说明技能为什么不能授予固件写权限。

练习二：画出可替换边界

画出当前模型、工具表、提示与会话版本，设工具表从 V3 切到 V4。规定切换发生在下一次决策前，并列出半写配置、未知工具与加载失败时应保留什么旧状态。

练习三：设计一个出域门

为船载质检工作站列四个只读或本地工具和一个受限投递工具。给每个工具写目标、载荷和副作用，构造“摘要里夹带原始报文”以及“目标重定向到公网”两条拒绝测试。

练习四：估算端侧预算

设模型 3B 参数、4-bit 权重，理论裸权重约 1.5 GB。另列量化元数据、KV 缓存、激活、索引和采集服务内存，不直接从权重得出能运行。说明需要在哪台设备测量峰值与长时发热。

回顾与自测

更新能力与限制数据流需要分别验收。配置成功加载不等于新 loop 正确，本地推理成功也不等于所有工具离线。

配置改动什么时候能生效？

取决于宿主实际读取与重建边界。下一步热载、显式 reload 和重启加载是不同策略，应以版本记录验证。

本地模型给出精确温度就可以发布吗？

不能。需追溯读取的记录、单位、时间与质检状态，生成数字不能替代测量。

端侧超出资源预算时应怎么办？

保留采集和安全控制优先级，减少上下文或停止分析，返回明确未完成项，不静默改用云端上传。
