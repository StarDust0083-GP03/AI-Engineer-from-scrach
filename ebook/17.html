从链到图

每天生成缺测统计可以是一条直线：读取、计算、保存。遇到异常温度时，流程可能需要检查标定、查询邻站、请求值班员确认，最后才发布报告。若把所有选择藏在一段模型提示里，重启后很难知道停在何处，也难以解释为何跳过了某项校验。

LangGraph 允许把应用显式表示为节点、边和共享状态。节点完成局部工作，边决定可到达的下一步，状态保存已经获得的事实与执行信息。模型可以在某个节点里选择工具，但图外层仍能限制它什么时候必须停下等人。

11-langgraph/ 包括课程、Agentic Chatbot 和 TripMate。它们提供图编排的不同观察入口。以下浮标流程是教学改造场景，源码事实仍按各项目实际功能说明，不能把新的质检字段当成这些项目已经提供的接口。

LangChain 与单 Agent

Chain 把处理顺序写进程序，单 Agent 把下一步交给模型，图则定义合法转移并允许节点内部保留自主性。三者可以组合：图中的“调查异常”节点可以包含一个有界工具循环，结果仍必须满足图状态的字段约定。

课程中的 LangChain 例子使用 ReAct Agent、工具适配和界面，适合查看 schema、执行器和观察回填怎样连接。迁移到新任务时，可以先只给两类教学工具：读取浮标记录与查询标定版本，观察单 Agent 是否能在预算内拿齐证据。工具必须返回时间范围和数据来源，不能只给无上下文数值。

create_react_agent 等同名函数在不同库与版本中可能指不同封装，AgentExecutor 也属于特定链路。阅读时核对 import 来源和依赖版本，不把课件里的名称直接拼成新 API。框架适配能省接线代码，但不能替代设备范围校验、缺测语义与模型异常处理。

多 Agent 研究系统

把异常分析分给取证者、解释者、报告者与复核者时，应明确每个角色的输入输出。取证者输出带编号的记录片段；解释者输出候选原因与支持程度；报告者只组织已获证据；复核者检查断言是否超出原始观测。角色名称不同不等于判断独立，若所有人都只读上一位的结论，最初的误读仍会一路传播。

课程的多角色研究流水线展示角色交接与批评回传。映射到质检时，复核者发现报告漏掉标定有效期，需要把具体失败断言交回解释环节，而非让报告者单纯换一种说法。这会产生回边，图结构因此比只前进的链更适合表示修订。

回边应有限制，比如最多两次补证或总计 20 秒的教学预算。共享状态保存证据 ID 和版本，避免整份聊天记录逐级复制；失败记录保留“缺的是哪条依据”，不只保留“请更严谨”。多角色的收益需在同样模型和预算下检验，不能从角色数推导准确率。

LangGraph 的核心

StateGraph 的状态可以理解为一份有字段所有权的任务记录。节点通常返回状态更新，而非任意修改所有字段。多个并行节点写同一键时，需要明确合并语义或 reducer，不能假定后完成的结果总该覆盖先完成的值。

图机制质检教学对应需要定义的边界
State设备、时间段、证据、草稿、审批状态哪些字段是输入，哪些是计算产物
普通边读取完成后计算输入字段必须已齐
条件边证据不足转澄清条件来源与空值处理
Subgraph复用一套标定核对过程子流程输入输出与父图映射
Checkpointer保留审批前后的执行快照存储持久性、线程键与版本
校验节点拒绝超出授权范围的读取不能只靠模型自报“合规”

一条有用的不变量是“没有 evidence_ids 不得进入可发布状态”。它应在程序边界检查，不能只写在 Writer 的角色说明里。每个条件最好能由保存的字段解释；若边的选择依赖无法追查的自由文本，图虽然画得显式，行为仍可能模糊。[1]

持久化与 HITL

审批等待期间重启进程，恢复依赖持久状态，而非前端还开着。Chatbot 与 TripMate 的本地示例使用 SQLite checkpointer 保存线程状态；同一个 thread 标识用于继续相同流程，不同标识应隔开历史。生产部署还要处理存储位置、访问控制与多进程连接。

教学任务走到“是否发布 B17 可疑观测说明”时，可中断并返回待审内容，包括设备、时间范围、证据摘要和草稿 hash。前端收到用户决定后将其作为 resume 输入交回同一线程。批准旧草稿后若内容变了，审批应失效，不能只因状态里存在 approved 就放行。[2]

使用 interrupt 时尤其要理解重执行语义：恢复通常会重新进入相应节点的代码，不能把中断前的外部副作用当成只执行一次。发送或写入应与幂等键绑定，或者移到批准之后的独立节点。检查点恢复图状态不等于事务性撤回网络调用，SQLite 的事务也不会自动覆盖外部报告服务。

实战一：Agentic Chatbot

Agentic Chatbot 展示对话界面、工具、PDF RAG、多会话与审批如何组装。它原有的业务工具是源码事实，学习时可以只观察“普通回答”“检索回答”“暂停等待授权”的三条控制路径，再设计自己的海洋质检工具。

源码能力边界可迁移的教学任务验收关注
工具目录读取浮标时槽与计算统计输入校验、错误类型与只读范围
PDF RAG检索传感器维护手册页码、型号、版本和证据片段
interrupt / resume确认是否外发质检草稿审批关联当前线程与草稿
SQLite 线程状态不同值班组保持独立任务恢复后仍然正确隔离
Streamlit 前端上传资料、看消息与待审项UI 不把等待态显示成完成态

项目对嵌入模型做懒加载，普通对话无需先加载全部 RAG 依赖。首次使用检索的额外延迟与模型调用慢应分开统计。更换嵌入模型时，新向量空间与旧索引不必兼容，应创建新索引并校验，而不是删除唯一现存库后再盲目重建。

维护手册上传成功只能证明收件，不证明已解析、向量化或可召回。界面应分别显示入库阶段，故障日志也应带同一文档任务号。没有命中时明确缺证据，不能由模型凭设备名称编造维护要求。

实战二：TripMate

TripMate 的实际项目领域是旅行规划，父图按顺序调用专家并共享 TravelState，采用 FastAPI 与 SQLite 检查点。本节保留它作为源码入口，但不沿用旅行问答案例，而用“浮标维护准备”解释相同的顺序交接约束。这是设计类比，原项目并未提供以下质检节点。

新教学编排，非 TripMate API
状态：设备 ID、故障证据、标定版本、维护建议、最终草稿
1. 观测专家：识别缺测与突变，不判断维修授权。
2. 标定专家：核对适用期与设备型号。
3. 维护专家：根据已确认故障列候选操作。
4. 汇总专家：保留依据与待确认项，不补造事实。
父图：规定顺序，并保存各阶段状态。

维护专家依赖故障证据，所以不能为了并行就提前按猜测开工。如果最后核对发现设备型号有误，前面的标定和建议都会失效。只向前交接的图需要明确回退路径或重规划规则，否则恢复只是从已有错误状态继续。

共享状态减少转述丢失，也可能传播陈旧字段。重跑观测节点时应清空或标记失效的下游建议，并记录数据版本。checkpoint 保存过去是什么，业务逻辑还需说明哪些过去结果仍然有效。

两个基础加固

异步和结构化校验决定了图节点能否稳定交接。异步适合等待独立 I/O，比如同时取两个设备的只读记录；计算密集或阻塞函数直接放进 async 节点仍可能阻塞事件循环。设置超时、并发上限与取消传播，比单纯使用 asyncio.gather 更重要。

Pydantic 可以检查设备字符串、起止时间和结果结构，但“两个时间字段都能解析”不保证结束晚于开始，也不保证用户有权读取该设备。应在模型之外验证跨字段约束和业务权限。对于缺测值，明确允许 null，不能让默认值 0 悄悄改变观测意义。

并行结果的合并同样需要契约。两个节点返回相同 evidence_id 时要去重，来源版本冲突时要保留冲突而非随意覆盖。类型正确、业务有效和授权允许是三道不同检查。

延伸对照：图编排的定位

图提供可执行结构，任务策略仍由开发者设计。框架自带持久化不意味着所有业务步骤都有正确恢复语义。

与推理模式的关系

规划与执行可做两个节点，反思可以在验证失败时回到调查节点，树搜索需要在状态里保存候选与预算。框架不会自动选择适合质检的评分函数；若把错误的候选原因打高分，图只会更稳定地执行错误策略。

与多 Agent 框架的关系

AutoGen 倾向描述谁接着发言，CrewAI 倾向描述角色承担什么任务，LangGraph 倾向描述状态怎样转移。这是便于阅读的对照，并非互斥能力边界。选型时可给三种方案同一条异常日志，比较证据保真、修订次数和暂停恢复，而不是只比较代码长短。

与持久化/工作流引擎的关系

恢复问题图需要的机制业务还需补充
审批中重启持久检查点与稳定线程键审批身份、内容版本及有效期

LangGraph 文档 和 LangChain 文档 可核对版本接口，Pydantic 文档 用于校验细节。Building Effective Agents 提醒从可验证的简单流程起步；只有明确需要分支和恢复时才承担图状态的维护成本。

动手验证

这些练习可先用固定节点返回值完成，不必访问外部模型或真实海洋设备。

练习一：把 Chain 改写成图

把“读记录、算缺测率、写草稿”画成直线，再增加“记录为空则询问时间段”的分支。设最多澄清两次，列出终止状态。检查空列表和工具失败是否被错误地归为同一事件。

练习二：给 Chatbot 加一条 HITL

在隔离副本中为“外发草稿”设计中断，待审状态保存 thread_id、草稿 hash 和目标地址。恢复时让批准只匹配当前草稿，拒绝或过期都不得调用发送 stub。不要用真实邮件练习。

练习三：制造一次恢复

暂停后关闭进程，再读取同一线程继续。让发送 stub 按任务幂等键记录调用，验证恢复不会重复发送。如果换一个线程 ID，解释为何找不到原待审状态。

练习四：判断该不该用图

分别评估“每小时缺测统计”“开放调查突变原因”“审批后发报告”三个需求。对每个需求写出最简单可行结构，以及升级到图能新增的具体控制，不能仅回答“复杂所以用图”。

回顾与自测

浮标质检流程的图设计要回答：字段从哪来，分支为何发生，暂停保存什么，以及恢复后什么动作允许重做。能明确这四点，框架名称才有实际意义。

有工具循环就必须用 StateGraph 吗？

不必。简单有界循环可以直接实现，需要显式分支、等待与恢复时图结构才更有价值。

检查点里的记录可以当作长期记忆吗？

它首先服务执行恢复，包含当时的任务状态。长期记忆要另做事实筛选、时效与跨会话检索，不能直接把所有 checkpoint 注入模型。

为什么重跑上游还要处理下游字段？

旧建议可能依赖旧证据。若不失效处理，最终报告会混用新观测与旧推断，结构正确却语义不一致。
