用一份报告解释整套多 Agent 系统

岸站要求生成本周的“观测完整性、异常候选、处理建议”。单个 Agent 可以起草，拆成多角色的理由应是证据检查与依赖清晰，而非希望更多模型互相赞同。摘要和异常扫描可以独立处理同一批记录，建议却依赖已经确认的问题，不能一开始就把所有分支当作独立工作。

04-multiagent/multi-agent-arch 的材料包含架构实验、完整分层 Notebook、框架练习和运维演示。模拟检索、NLI、内存 Trace 和 MockLangSmithClient 用于呈现接线，不代表访问了真实平台。索引提及的部分拆分文件在快照中并未单独出现，相应内容可在 02_hierarchical_multi_agent_demo.full.ipynb 追溯。1

本章重新设计周报任务与数值，原项目没有因此接入浮标观测。每个角色都应交付带证据编号的结构化产物，避免从一个自由文本摘要传到另一个自由文本摘要时丢掉依据。

从输入到人工批准：一条完整轨迹

教学任务 J52 处理 7 天、3 台浮标的周报。文件范围、时间标准与接收值班组在收件时固定，所有角色带相同 job_id，但只接收自己所需的字段。

  1. 取证器先确认访问范围，返回记录批次 E12 与维护记录 M8。若某台设备缺一整天，状态写明资料缺口，不以空列表冒充全天正常。

  2. 完整性 Worker 统计应有时槽与实收数，异常 Worker 标出突变候选，两者可并行读取 E12。标定核对若依赖维护记录，可独立处理 M8。

  3. 建议 Worker 等待异常与标定结果，只对已确认条件给建议；不确定原因写为待查，不把“温度跳变”直接等同传感器损坏。

  4. 汇总器生成固定栏目并保留来源。复核器拆出 12 个可核验断言，其中 9 个有支持，教学支持率为 9/12=0.75。

  5. 假设自动交付门槛设为 0.85，且关键设备结论必须全部有据。此草稿转人工，票据列出 3 个失败断言、原片段、草稿版本及允许操作。

  6. 审核人要求修订后，形成新草稿版本再复核。批准只对应当前版本与目标，不把一次批准永久应用于以后周报。

门槛是本章教学配置，不是海洋行业标准。平均支持率也不能掩盖关键结论错误，必须单独检查不允许失败的断言。

并行的收益应该怎么算

教学耗时设为取证 0.15 秒、完整性 0.35 秒、异常扫描 0.45 秒、建议 0.20 秒、复核 0.10 秒。串行总计 1.25 秒；前两项分析并行且建议等待二者时，关键路径为 0.15+max(0.35,0.45)+0.20+0.10=0.90 秒，理想节省 0.35 秒，未计队列和汇总开销。

若把建议也放进 max，会错误消除它对异常结果的依赖。并行减少墙钟等待，不自动减少模型调用数量和 token。超时后的部分结果能否交付也要提前规定，不能由最先完成的 Worker 临时决定。

架构基础七个实验，各自回答什么

实验形式新周报任务中的用法检查边界
01.1 单体顺序完成统计、扫描、建议作为最简单基线，保留各阶段结果方便定位
01.2 Pipeline批次经队列流向下阶段慢阶段造成积压时有容量与停机信号
01.3 Hub-and-Spoke中心分派各设备只读分析部分设备失败时报告整体与局部状态
01.4 Blackboard共享板保存证据、断言与审核每字段明确写入者与版本
01.5 幂等J52 重投递不重复发周报认领、发布结果与唯一键需要可靠存储
01.6 可观测各 Worker 与父任务关联父子调用不能重复累计成本或时延
01.7 降级生成失败时只返回统计与证据明确缺少解释，不能标完整周报

共享 owner 字段不等于锁。两个 Worker 都读到 pending 后再写 owner，仍可能双重认领，需要条件更新、事务或可靠队列。演示中的数据库事务也不能让另一个独立 Redis 写入自动参与同一事务；跨系统副作用应使用目标服务的幂等键或适合的消息协议。

把周报结果与去重状态放在同一事务域可以减少窗口，但网络发送已经发生而结果未保存时仍需查询或重试策略。架构图上的“原子”字样不构成证明，应追踪真正执行副作用的边界。

03–08：框架换了，职责没有变

不同框架可以承载相似责任，阅读时先找到下一执行者如何确定，再看状态与证据怎样传递。

AutoGen：看谁接着发言

GraphFlow 适合固定路径，SelectorGroupChat 由选择器决定下一发言者。用于周报时，后者可能让核对者追问缺失依据，但必须限制回合与重复请求。ListMemory 提供可供读取的记录，不自动具有持久存储、设备隔离和有效期治理。

检查对话式协作时，应确认终止词由谁生成、出现在哪条消息，以及失败角色是否仍被记为完成。一次角色说“完毕”不代表它的证据或统计正确。

CrewAI：看任务交给哪个角色

Sequential Crew 可按取证、分析、写作顺序组织，Hierarchical Process 让管理模型分派任务。角色说明表达职责，工具端仍需限制设备与路径。把维护记录接口接到真实服务后，延迟、授权和错误都与 mock 不同，需重新测依赖与失败处理。

若多个角色实际共用同一上下文并重复复述，拆分可能只增加成本。可以对比独立输入与共享摘要两种设置，检查复核是否真的发现上游故意植入的错误。

LangGraph：看状态沿哪条边流动

状态图可明确写出取证、分析、建议、复核和人工节点。验证失败应把失败断言带回指定上游，清除受影响的下游结果，而非把“再想想”广播给所有人。条件边依据结构化状态，预算字段限制回边次数。

课程练习从流水线、队列 Worker 到 Supervisor 与 HITL，分别锻炼依赖表达、并发认领和受控交付。工程总结中的 Schema、幂等与 Trace 是框架之外也需要的契约，不会因为使用某个库自动生效。

09：从“会回答”到“可运营”

一个 Run 可表示一次模型或工具调用，parent_run_id 把它们关联成 Trace。父任务的等待时间已覆盖子任务执行，不能把父子时长再相加。模型 usage 则应按真实叶子调用聚合，避免父层汇总又被累计一次。

运维现象先看什么有依据的处理
断言错误对应 E12/M8 片段与转换区分取证缺失和生成新增
周报变慢队列等待、各分支完成时间优化关键路径而非只看平均调用
费用增加迭代、重试、输入输出 usage减少重复取证或约束预算
升级后退化同题集、同评分器逐题结果按明确容差阻断发布
人工审核积压失败类型、票据年龄与责任人改进证据或分流，不能放低门槛掩盖

教学基线支持率为 0.92，允许相对下降 2%，最低为 0.92*(1-0.02)=0.9016。新结果 0.90 略低于线，应判失败。若政策说下降 2 个百分点，下限却是 0.90；两个口径必须分开写，不凭文字印象判断。

令牌桶限制长期速率并允许短突发，信号量控制在途数量，总预算限制整个任务费用。三者分别防止限流、资源耗尽和持续烧费，队列也要有容量。09 材料中的质量分与平台客户端有模拟成分，不能当作真实 RAGAS 或 LangSmith 的运行结果。2

不用写代码的架构验收

异常扫描还未完成，能否先让建议角色输出最终维护动作？

不能将其作为基于事实的最终建议。若确需提前准备，只能生成标注为候选的方案，并在异常与标定结果齐备后重新核验。

认领记录中只有一个 owner，是否证明从未重复执行？

不证明。两个 Worker 可能先后覆盖同一字段。需要认领操作的原子结果、执行日志和副作用幂等记录。

支持率达到阈值，为什么仍可能不得外发？

阈值只反映某种质量。关键断言、访问权限、接收人和审批政策仍需满足，任何一个硬条件失败都可以阻止发布。

纸上验收可给 J52 注入一个错误设备编号、一条过期维护记录和一次重投递，分别预测由哪个角色或程序门检出。若只能回答“监督者会发现”，说明边界还未落实。
