上线后的两条硬约束

早高峰值班员同时发来很多查询：有的只是解释车辆状态字段，有的要综合多个站点与运输约束。全部交给同一高成本模型会浪费预算；全部交给低成本模型又可能漏掉复杂约束。模型服务暂时不可用时，也不能让助手猜测站点库存。

这里有两类边界。资源边界包括费用、并发和等待时间，业务边界包括证据有效性、工具权限和能否产生副作用。低价但错误的搬运建议，或很快返回的过期库存，都不是有效降本。

一次请求应记录选路、每次尝试、是否降级、命中缓存及实际 usage。成本不能只记最终成功的模型；超时请求可能已经被服务执行，回退模型又产生一笔费用。权限检查和审计也不能因为主模型故障而被降级跳过。

本章的模型名采用抽象能力档位，价格和 usage 为教学输入，不引用未经核验的产品档位。代码只演示政策与计算，不连接模型或真实工单系统。

请求闭环

用同一个 request_id 连接所有分支，避免降级或缓存命中后丢掉请求来源。图中显示各阶段会留下的证据，而不是只画一条成功箭头。

模型路由

先按风险和能力要求筛选可用模型，再考虑价格。解释字段可以走轻量路径，多站路线比较走推理路径；创建工单则无论使用哪个模型，都要经过确定审批。路由不应成为绕过验证的捷径。

档位和预算单位均为教学设定，不是供应商产品列表
def choose_model(task, budget):
    if task["kind"] == "create_order":
        return {"path":"approval_workflow", "model":"reasoning", "reason":"写操作需审批"}
    if task["needs_multi_hop"]:
        if budget < 2:
            return {"path":"defer", "model":None, "reason":"复杂任务预算不足"}
        return {"path":"answer", "model":"reasoning", "reason":"跨站约束"}
    return {"path":"answer", "model":"compact", "reason":"单步解释或读取"}
assert choose_model({"kind":"query", "needs_multi_hop":True}, 1)["path"] == "defer"

复杂度由规则或分类器判断，都有漏判风险。可先为明确的业务类型固定路径，再对开放请求训练路由器。在线应抽样将低档位结果与高能力基线比较，关注难题被误分为简单题的比例。便宜模型先试再升级时，要把第一次输出和评估开销算进总成本。

熔断与退避重试

熔断器保护故障中的下游，重试则处理可能恢复的单次失败。两者触发对象不同：权限拒绝和参数错误不应累计为供应商故障；连接超时和服务错误则可能计入。

CLOSED

调用前状态允许行为转移
CLOSED正常请求达到故障阈值后 OPEN

OPEN

调用前状态允许行为转移
OPEN拒绝普通请求冷却结束后准许受限探测

HALF_OPEN

调用前状态允许行为转移
HALF_OPEN只放一个或少量探测成功恢复，失败重新冷却
单线程三态示意，省略 CLOSED 故障累计；并发生产实现需原子预留探测位
class ProbeGate:
    def __init__(self):
        self.state, self.busy = "CLOSED", False
        self.until = 0
    def allow(self, now):
        if self.state == "OPEN":
            if now < self.until:
                return False
            self.state = "HALF_OPEN"
        if self.state == "HALF_OPEN":
            if self.busy:
                return False
            self.busy = True
        return True
    def finish(self, ok, now):
        was_probe = self.state == "HALF_OPEN"
        if was_probe:
            self.busy = False
        if ok:
            self.state = "CLOSED"
        else:
            self.state, self.until = "OPEN", now + 10

在改变状态前保存 was_probe，可避免失败后状态已变 OPEN，清理分支再也进不去的问题。原仓库熔断示例值得重点核对这种状态变更与计数释放的先后。取消和异常也必须释放探测位，否则半开可能永久卡住。

退避可以采用 full jitter：在 0 到 min(cap, base*2^attempt) 间随机等待。供应商有 Retry-After 时还应按其规则处理。随机抖动用于分散大量客户端的重试时间，不是为了提高单次模型质量。

每次重试前检查总截止时间和剩余金额。读取可以重试，创建工单超时则不能假定没有执行；应按幂等键查询回执或重试同一业务操作。只靠“超时后换模型”可能重复创建任务。

降级链

降级的目标是保留能保证的功能，不是强行生成一段回答。库存服务不可用时可以解释字段或展示带时间的旧快照，但不能声称完成了本次实时查询。跨站路线缺乏完整证据时，可以返回尚缺哪些信息。

教学代码，可离线检查；不连接业务服务
def unavailable_answer(task, cached_snapshot=None):
    if task == "explain_status":
        return {"status":"degraded", "mode":"static_help", "text":"请参照状态字段说明。"}
    if cached_snapshot is not None:
        return {"status":"degraded", "mode":"stale_snapshot",
                "snapshot":cached_snapshot, "may_dispatch":False}
    return {"status":"unavailable", "mode":"no_evidence", "may_dispatch":False}
assert not unavailable_answer("live_stock")["may_dispatch"]

备用模型应该满足相同的数据权限和输出约束，且尽量不共享同一故障域。所谓更小模型未必更可用，也不保证更快；链的顺序应由能力、独立性和预算决定。[2] 把业务成功、降级展示与服务不可用分开统计，避免模板返回掩盖真实完成率。

计费与对账

按次记录账本，再汇总到整项调度任务。至少保存模型版本、输入与输出 token、缓存计费口径、价格版本、重试编号和 usage 是否最终确认。估算用于预算预留，结算以服务返回或账单为准。

美元单价为教学值；不代表任何供应商当前价格
from decimal import Decimal
def estimate_cost(input_tokens, output_tokens, in_rate, out_rate):
    million = Decimal(1_000_000)
    return (Decimal(input_tokens)*in_rate + Decimal(output_tokens)*out_rate) / million
cost = estimate_cost(1200, 300, Decimal("0.50"), Decimal("2.00"))
assert cost == Decimal("0.0012")
def discrepancy(estimated, actual):
    return {"delta":actual-estimated,
            "relative":None if estimated == 0 else abs(actual-estimated)/estimated}

输入 1200、输出 300，在教学费率下分别花 0.0006 与 0.0006 美元，总计 0.0012。若两次尝试都计费，应累计两笔，而非仅保存最终答案那笔。[1] 使用 Decimal 可以减少金额计算的二进制浮点误差，但仍应按账单规定舍入。

本地估算为零而实际有费用时，相对误差没有普通定义，应单独标记，不能用随意替换分母掩盖异常。长期偏差要检查 tokenizer、工具参数、缓存 token 和额外计费项，不要靠不断提高告警阈值让告警消失。

缓存与误命中

精确缓存也需要完整键。相同问题字符串在不同租户、不同权限或不同规程版本下，答案可以不同。只对 prompt 求哈希不是零风险设计。缓存写入之前还要确认答案经过相应验证，防止失败文本长期复用。

缓存准入片段：semantic_score 由检索器提供，并非答案等价概率
def cache_match(entry, request, now, semantic_score, threshold=0.9):
    if entry["tenant"] != request["tenant"]:
        return False
    if entry["permission_scope"] != request["permission_scope"]:
        return False
    if entry["knowledge_version"] != request["knowledge_version"] or now >= entry["expires"]:
        return False
    if entry["intent"] != request["intent"] or entry["entities"] != request["entities"]:
        return False
    return semantic_score >= threshold and entry["verified"]

“停运 BIKE-031”和“恢复 BIKE-031”在词汇和向量上很接近，动作却相反。语义缓存应先核对意图、实体和否定方向。实时库存通常不适合长时间缓存；即便精确命中，读取快照的 TTL 也不能保证可直接据此执行搬运。

L1 进程缓存与 L2 共享缓存要协调过期和失效。规程更新后，若只清 L2，旧 L1 仍可能返回过时处置。可以在键中包含不可变知识版本，统一切换版本；同时用并发合并或锁减少同一未命中请求对下游的瞬时冲击。

工具权限分层

工具治理要在实际执行入口检查。模型使用高能力档位不应因此拥有更高权限。只读查询、建议生成、工单创建与车辆状态修改可以分成不同能力集，并对敏感写入要求审批。

授权片段：完整实现还需校验参数 Schema、审批人、期限与重放次数
def authorize_call(actor, tool, args, approval=None):
    allowed = {"viewer":{"read_station"}, "dispatcher":{"read_station","create_order"}}
    if tool not in allowed.get(actor["role"], set()):
        raise PermissionError("tool_forbidden")
    if args["tenant"] != actor["tenant"]:
        raise PermissionError("tenant_mismatch")
    if tool == "create_order":
        if approval is None or approval["payload_hash"] != actor["payload_hash"]:
            raise PermissionError("approval_required")
    return True

Schema 检查形状，业务规则检查数量与站点范围，审批检查具体动作是否被同意。审批绑定请求摘要后，模型若把搬运量从 5 改成 8，应重新审批。审计既记录准许也记录拒绝，敏感参数可脱敏或引用安全存储，不宜把全部凭证和维修记录写进日志。

灰度与蓝绿

发布的不只是模型，还包括提示词、工具 Schema、路由策略和知识索引。它们最好形成一个可回滚的配置版本。金丝雀先让一部分稳定分组接受新版本，蓝绿则维护两套环境再切换入口。

教学代码，可离线检查；不连接业务服务
import hashlib
def version_for(team_id, percent, salt="bike-route-v2"):
    if not 0 <= percent <= 100:
        raise ValueError("灰度比例不合法")
    digest = hashlib.sha256(f"{salt}:{team_id}".encode()).digest()
    bucket = int.from_bytes(digest[:8], "big") % 100
    return "candidate" if bucket < percent else "stable"
assert version_for("day-team", 0) == "stable"
assert version_for("day-team", 100) == "candidate"

按团队而不是单次请求分组，可以减少同一班次规则来回变化；但分组单位也会影响统计独立性。固定哈希不是随机实验效果的保证，需要检查两组任务分布。放量门槛应包含关键错误、降级率和费用，而不只看 HTTP 成功率。回滚还要确认旧版本能读取当前状态，不能只切回旧进程。

Trace 与治理

一条 trace 应把缓存、选路、熔断、模型尝试、工具调用、证据检索、验证和账本连成父子关系。对值班员看到的一个答案，能够追到所有重试及最终采用的快照，才有排障价值。

生成后治理可以先检查引用和证据版本，但引用字符串存在不代表事实被支持，自报置信度也未必校准。下面将关键断言检查结果作为输入，区分格式完备与内容通过。

教学代码，可离线检查；不连接业务服务
def generation_gate(answer, valid_sources, claim_checks):
    if not valid_sources:
        return {"ok":False, "reason":"no_valid_evidence"}
    if not any(f"[{sid}]" in answer for sid in valid_sources):
        return {"ok":False, "reason":"citation_missing"}
    if not claim_checks or not all(claim_checks):
        return {"ok":False, "reason":"claim_not_supported"}
    return {"ok":True, "reason":"accepted"}
assert not generation_gate("可直接投放 [B4]", ["B4"], [False])["ok"]

事前从可信语料准备证据，事中验证引用与断言，事后按用户纠错和人工抽查更新回归集。三层相互补充，不能因事后有反馈按钮就放松写工具审批。运行日志应采用最小必要信息，trace 平台也属于数据访问边界。

延伸对照：成本与可靠性的成熟经验

可靠性模式来自分布式系统，模型路由与语义缓存又带来新的质量判断。迁移通用模式时，要把非确定输出和调用费用放进原有设计。

熔断与重试

Release It! 及相关工程实践系统化了熔断思想，AWS 的退避指南讨论指数等待与抖动。模型 API 也需要这些保护，但一次生成常比普通 RPC 更慢、更贵，重试策略应遵守任务总期限。SDK 自带重试和应用重试叠加时，还要检查最大尝试数是否相乘。

LLM 特有的成本研究

FrugalGPT 研究模型级联，RouteLLM 用偏好数据学习请求分配。它们的效果依赖任务分布、模型对和质量判据，不能直接套到维护工单上报节省比例。

语义缓存如 GPTCache 关注相似请求复用，但维修动作和时效约束要求更严格的等价检查。缓存率提升若伴随故障码误匹配，可能是风险扩大而非性能成功。

动手验证

用固定响应与虚拟时钟模拟整个请求链。不要用真实写工具测试重试，避免制造重复工单。

练习一：跑通闭环并观察账本

为主模型安排超时、备用模型安排成功，记录两笔尝试。给两次响应各一组 usage，用本页费用函数合计；再将备用也失败，检查结果是 unavailable 而非 answered。验证账本包含失败尝试的待对账标记，最终结果带 degraded。

练习二：验证熔断状态迁移

用数值时间 0、5、11 驱动 ProbeGate。失败后 open 到 10，时间 5 应拒绝，11 应进入半开，第二个并发探测应被拒绝。让半开失败，断言 busy 已释放且进入新的冷却。再测试取消路径，避免遗漏清理。

练习三：找出语义缓存的误命中

放入“停运 BIKE-031”的缓存，查询“恢复 BIKE-031”。即使人为传入相似度 0.99，也应因 intent 不同拒绝。再分别改变租户、权限范围、知识版本和时间，确认每种变化都能使缓存失效。

练习四：给路由加一个复杂度判定

先用规则区分字段解释、跨站比较和工单创建，手写至少一个每类样本以及一个歧义请求。记录误分原因，再决定是否引入分类模型。不要只按问题长度判断，短句“恢复全部车辆”也可能是高风险写操作。

回顾与自测

一次回答的真实成本包括失败尝试、降级和验证，真实成功则要求业务证据与权限均满足。路由、缓存和回退都不能改变这条验收边界。

精确缓存是否天然安全？

不是。键缺少租户、权限、知识版本或时效时，同样文字也会返回错误或越权结果。

模型调用超时后能否立刻换模型重做写操作？

不能先假定原操作没发生。使用业务幂等键和回执查询，确认状态后再恢复，审批也应绑定同一动作。

为什么模板回退不算业务完成？

它可能保住接口可用，却未完成实时查询或路线验证。应单列降级与不可用，不让成功率掩盖证据缺失。
