可读蓝图

一个岸站先只接入几十台浮标，不需要同时建设多平台网关和复杂插件市场，却仍需要回答有依据、数据不串组、失败可定位。12-hermes-agent-small/ 中的 waku 适合观察这些最低限度的工程责任如何拆开。代码少让调用关系容易检查，不表示已经具备大规模生产系统的全部保护。

本章把“检查 B17 昨夜缺测并生成交班说明”作为任务。请求来自哪里、模型读了什么、工具改了什么以及最终是否可发布，各有单独的负责人。对一个本地优先助手而言，SQLite 里的记录和 JSONL 轨迹就是可以直接检查的证据，而非隐藏在服务里的黑盒状态。

组件本任务里的判断可留下的证据
Harness使用哪个会话和配置装配版本、输入来源
Loop继续读数据还是返回回答模型与工具次序
Memory是否需要过去的标定信息门决策、召回来源
Eval / Ops报告是否满足契约结构化断言与评分记录

“昨夜缺测率是多少”若当前工具结果自足，可以不查个人记忆；“和我上次认可的报告格式一致”则需要历史约定。读路径的门和写路径的巩固彼此独立，跳过一次检索不表示本轮对话不用保存。

Ops

Trace 将这次门控、各次迭代和工具参数关联到 Q31。确定性评测可检查设备 ID 与时间范围，主观评委可评价说明是否清楚。两份结果分别保留，不能让语言表达高分抵销工具读错设备的失败。

Harness：装配与网关

waku/app.py 是理解启动装配的入口。配置、数据库连接、记忆、工具表、会话和追踪对象先构建好，再由 Waku.respond() 接受消息。CLI、Telegram、语音或 Dashboard 将输入转成文本，平台差异尽量停留在入口，不扩散到工具循环。

基于接线顺序的教学片段
收到文本：检查 B17 昨夜的记录
  session.build_system(message)   → 本轮提示
  recent history + message        → 消息序列
  run_loop(...)                   → 回答与调用记录
  session.add_exchange(...)       → 保存本轮交换
  memory.maybe_consolidate()      → 判断是否到巩固时机
  tracer.end_turn(...)            → 完成追踪记录

这里每轮构建工作上下文，与 Hermes 的会话级冻结策略不同。默认单位被修改后，下一轮可能直接读取新值，实现较直观；代价是前缀更容易变化，无法默认推断供应商缓存仍有相同收益。应比较真实请求内容与缓存 usage，而非从“复用了 Session 对象”推断命中。

保存和巩固之间也有失败窗口。如果回答已经返回、chat_log 已写，而巩固调用失败，至少应能从未处理日志再次尝试。若保存失败却向用户承诺“我以后会记得”，就超出了已发生的状态变化。教材里的调用顺序可以帮助发现这种承诺与持久化的错位。

Loop：95 行循环

标题中的行数描述教学版本的规模，不是接口契约。更有用的是跟踪退出路径：模型给出无需工具的响应时自然结束，达到 max_iterations 时预算结束，外部错误或取消则走相应异常边界。

质检循环的伪代码
for iteration in range(max_iterations):
    reply = model(current_messages, available_tools)
    if not reply.tool_calls:
        return final_text(reply)
    for call in reply.tool_calls:
        observation = dispatch(call)
        append_paired_result(call.id, observation)
return budget_exhausted_response()
# 伪代码只说明控制流，不是 waku 的直接 API。

一个回复可包含多个工具调用，教学实现逐个执行。若读取 B17 与 B18 都独立，也不能据此假定已经并行；并发需要另外处理结果配对、取消和访问共享资源。模型返回未知工具时，应产生明确错误，不能让名字相近的工具自动代替执行。

observer 把 llm、tool、text 等事件送给外层。Dashboard 可以显示进度，Tracer 可以追加日志，流式输出还会产生文本增量。循环不必知道哪个订阅者在画界面，但订阅者异常是否被隔离仍取决于实现，不能从“使用 observer”直接推断永不影响主任务。Provider 适配在 loop/models.py 统一消息方言，换模型时仍需验证工具协议支持。

Memory：门与三支柱

语义、情节与程序性记忆适合回答不同问题。报告习惯是可持续事实，昨夜掉线是带时间的经历，怎样核对漂移是工作方法。它们一起进入上下文时应保留这种区别，不能把一次临时处置变成所有设备的永久规则。

类型教学记录读写边界
Semantic交班报告采用 UTC更新时检查旧约定是否被明确替换
Episodic06 月 12 日 B17 断链 40 分钟保留发生时间与出处，不说设备现在仍断链
Procedural缺测质检步骤的 SKILL.md命中后加载操作知识，不因此获得写权限

本地语义和情节数据可由 SQLite FTS5 搜索，可选向量后端承担另一种召回方式。关键词搜索有利于设备编号精确命中，语义检索适合自然语言相关问题，但两者都需要设备和用户范围过滤。每轮 system 构建发生读取，回合保存后才判断巩固，读取的新鲜度取决于之前写入何时成功。

检索门：先问要不要

检索门先判断当前请求是否依赖记忆，再决定是否访问存储。比如“计算 6/72”自带输入，查历史只增加噪声；“按我上次认可的口径算缺测率”隐含旧约定，需要检索。门返回是否检索、搜索词与理由，后两者让路由结果可追查。

新教学输入，不调用模型
自足计算：
{"retrieve": false, "query": "", "reason": "输入已给出分子分母"}
引用历史：
{"retrieve": true, "query": "缺测率 统计口径 上次批准", "reason": "需要既有约定"}
解析或调用失败：
采用源码的 fail-open 路径，使用当前消息尝试检索。

fail open 指门控失败后继续检索，不是绕过权限。它牺牲部分延迟和噪声控制以减少漏召回，不能笼统说陈旧信息总比没有信息安全。在浮标业务中，过期标定系数若被误用可能更糟，因此召回结果仍需带时间与来源。[1]

还要检查门控模型输出 JSON 的能力。预算过小、推理内容挤占输出或格式不合规都会触发降级。监控可以分别记“模型判定 retrieve”和“门失败后 retrieve”，否则检索比例升高时很难判断是任务变化还是门正在故障。门本身一次额外调用的成本也应计入总延迟，短任务未必一定更省。

巩固：每 N 轮蒸馏

巩固把累积的对话提炼成可复用事实与事件，而非每个工具输出都直接写长期库。教学设定每 4 轮处理一次：前 3 轮先保存 chat_log，第 4 轮提取“默认 UTC”和“B17 当晚曾断链”，成功写入后标记对应日志已处理。这里的 4 是纸上配置，实际 N 以项目设置为准。

批处理让抽取器看到用户纠正。例如第一轮说“用本地时间”，第三轮明确改为 UTC，合并处理应保留最终有效约定及变更来源。它也带来延迟：尚未巩固的信息可能只能从近期对话读取，不能指望语义库已经更新。

一致性检查很重要。先标记 processed 再写事实，失败会丢更新；先写事实再标记而无幂等，重试可能生成重复。阅读 consolidation.py 时可重点追踪这两步是否处于事务或具备去重策略。蒸馏后的描述还应能回到原对话，便于用户纠错和删除，不能只留下无法解释的事实句。

Eval 与发布门禁

确定性评测检查结构化行为，LLM 评委判断语言层面的质量。前者可以断言读取范围是 UTC 的昨夜，后者可以判断说明是否解释了缺测与异常值的差别。分别运行、分别记账，才不会把模型的随机评分混入稳定的单元测试。

在 waku 项目目录中选择运行
# 先验证可重复的调用契约。
uv run python -m pytest -q evals/deterministic/
# 评委用例可能访问模型，单独核对运行条件。
uv run python -m pytest -q evals/judge/
# 汇总结果并用退出状态表达是否放行。
uv run python -m waku.ops.release_gate

release_gate 汇总为 .waku/eval_report.json。判断放行时既看确定性是否全部满足，也看配置要求的 judge 阈值，不应把它描述成只有某一种检查有权阻断发布。[2] 缺失报告、评委超时或测试未执行也应与“全部通过”区分，具体退出语义需读实现。

Trace 负责记录门、迭代和工具行为；报告解释失败；门禁据政策返回退出码。Dashboard 展示有助于人看过程，但界面看起来正常不能证明持久化、设备范围和缺测计算正确。升级提示或 Provider 后应重跑相同题集，保留旧报告以比较变化。

阅读路径

阅读顺序按数据流安排：先确认状态落在哪里，再看请求如何流过循环，最后看记忆和评测怎样旁接。每次阅读都拿 Q31 这条任务作定位对象。

入口要跟踪的值完成这一步的标志
config.py、app.py数据库路径、模型配置、依赖对象知道重启后从哪恢复记录
runtime/session.pysystem 与历史窗口能列出模型真正看到的材料
loop/agent.py、工具表调用 ID、迭代计数、退出原因能区分自然结束和预算耗尽
memory/门决策、命中记录、巩固标记能解释新偏好何时可被召回
ops/ 与 evals/Trace 与评测报告关联失败能够定位到结构或回答质量

skills/ 用于助手的方法知识，.claude/skills/ 中的贡献流程用于开发者工作。两类文件的受众和执行时机不同，不能把项目维护说明无条件塞进每次质检上下文。

延伸对照：极简实现与生产系统之间

小型工程省略了许多产品能力，但仍可以借助对照检查设计是否自洽。读文献和完整产品时，以具体能力为单位比较，避免按代码行数比较可靠性。

记忆的研究脉络

Generative Agents 可用于观察事件记录怎样影响后续行为，MemGPT 关注上下文容量与外部存储的调度。Mem0 的事实整理与 Zep 的时间关系可以启发不同测试：同一设备的旧事件不能覆盖新状态，同一用户的偏好也不能无边界跨组共享。waku 的门控属于是否读取的策略，巩固属于怎样写入的策略，二者不能互相替代。

极简与完整的取舍

选择小系统的便利规模扩大后的问题
每轮现拼提示新偏好生效路径容易理解缓存与多会话视图需重新评估
本地 SQLite便于备份、查询和删除并发写、迁移和多机访问需规划
小型工具循环容易逐步读懂审批、后台任务和取消需要补接口
统一事件观察界面和日志共用轨迹监听失败和敏感数据传播需治理

Hermes 与 waku 的选择可以相互解释，但不能把前者的某项能力默认算到后者头上。声称支持恢复或隔离时，要给出对应实现和测试。

可直接借鉴的四条

可以先复用事件接口而非复制 UI 逻辑，用结构化输出约束门控，以数据库记录而非模型口头承诺确认记忆写入，再让发布命令同时检查结构与质量。每项都需要失败样例：监听器抛错、门输出坏 JSON、巩固重试和 judge 不可用。只验证正常输入不足以证明这些边界有效。

动手验证

所有故障注入都应放在副本或 mock 依赖中，不修改真实凭据、不触碰正式观测库。

练习一：验证检索门

准备“算 6/72”和“按我上次认可的缺测口径计算”两条输入，预测门的不同决策。用 stub 模拟门控超时，确认其降级后仍执行用户范围过滤。记录 reason，不能只统计是否发生搜索。

练习二：跟一轮多工具迭代

给循环一个固定回复序列：读记录、算缺测率、返回说明。检查三次模型迭代与两次工具执行，并把上限设为 2，观察预算结束是否仍被界面标为完整成功。将未知工具名插入一次，确认错误能绑定正确调用。

练习三：给 waku 加一个工具

在练习副本新增一个只读工具，输入时槽总数与缺测数，返回缺测率。用总数 0、缺测数大于总数和正常的 6/72 做确定性测试。即使算式简单，也要拒绝无意义输入，不能让模型自行决定分母为零时的值。

练习四：让发布门拦一次

让一个确定性用例故意读取错误设备，运行发布门并核对非零退出与报告中的失败项。恢复后再跑同一题。若 judge 未运行，明确记作未测，而不是因为无分数就算达到阈值。

回顾与自测

对这个小助手，最值得检查的是三次转换：文本变成一次请求，对话变成长期事实，测试结果变成放行决定。每次转换都可能丢失身份、时间或失败信息。

门控比直接检索多一次调用，什么时候仍值得？

当大量请求不需要历史、检索较贵或无关召回明显干扰回答时可能有收益。应比较总延迟、漏召回与噪声，不能假定小模型一定免费。

巩固周期到了，为什么还不能说已记住？

达到周期只触发工作，抽取、写入和标记都需成功。报告应根据持久化状态，而不是根据调用开始来承诺。

订阅了 observer 是否自动获得异常隔离？

不会。还需核对调用方式、异常捕获和超时策略。接口解耦减少循环依赖，不等于订阅者错误不再存在。
