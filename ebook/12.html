把验证交给机器

助手改完库存计算，在本地看到测试通过，却可能漏装依赖、只测了一个函数，或在测试后又改了接口。团队需要在受控环境里重新运行验证，并将结果绑定到代码版本。持续集成提供这一共同检查入口，而非信任某个会话的口头回报。

本章继续使用 movable=max(0,present-locked-reserve) 的教学需求。快速门禁验证核心算术和接口契约，较慢的回归检查车型、站点数据与展示组合，发布前再检查最终制品。不同门禁可有重叠，关键是用风险与时延说明选择，不是把同一条命令复制四次。

CI 结果要反馈给 Agent 和评审者：哪条断言失败、用什么输入、期望和实际分别是什么、怎样复现。只有“Pipeline failed”无法指导修复。反过来，流水线绿色也只说明已定义的检查通过，测试盲区和权限风险仍需独立评审。

这里的 YAML 为新编教学配置，不修改仓库共享构建文件，不连接真实 GitLab 或 Jenkins，不执行部署。读者可在自己的隔离练习仓库中补齐测试和依赖。

CI、交付与部署

先区分代码验证与发布决策。持续集成产出可追踪的检查结果，持续交付保持制品可发布，持续部署则在门禁后自动进入目标环境。采用哪一种取决于风险政策，不应以“多数企业怎样”代替自己的决定。

方式自动到哪一步本案例的人工边界
CI构建与测试评审差异与业务风险
持续交付产出可部署制品批准生产切换
持续部署满足门禁后自动切换事前制定风险与回滚政策

核心概念

Pipeline 是一次完整执行，Job 是可调度任务，Stage 是默认阶段屏障。GitLab 中具体 shell 命令通常写在 script 列表里，“Step”不是与所有平台完全一致的独立对象。Runner 执行 Job，Artifact 保存正式产物，Webhook 是事件通知机制之一。

对于库存功能，lint、test 和 build 可以是不同 Job。默认阶段规则让后续阶段等待前一阶段成功，needs 则声明明确依赖，使部分任务不必等待所有无关 Job。并行能否真正发生还取决于 Runner 容量和资源限制。

分支策略和 CI 相互影响，但没有唯一正确方案。小步合入有利于缩小回归定位范围，MR 门禁则需要仓库设置真正要求成功状态。仅在 YAML 写一个测试 Job，不代表合并按钮已经被政策阻断。DevOps 还涉及协作、反馈与运营责任，CI/CD 是其中一部分。

pytest 与门禁分流

测试发现和选择决定门禁实际覆盖什么。pytest 默认寻找 test_*.py 或 *_test.py 等测试文件，再发现 test_ 函数与合规测试类；项目配置可以改变规则。marker 需要注册，开启 strict-markers 可防拼写错误导致误选。

门禁建议覆盖本案例的边界
MR 快速纯函数、关键接口数量边界和字段契约
主干关键回归接口到显示、数据映射避免二次扣除
Daily组合与较慢端到端不同车型和空库存
Release对最终包的验收制品内容、启动与回滚兼容
配置与命令说明，分开放入 pytest.ini 和终端；不是一个可整体运行的脚本
# pytest.ini 的教学配置
[pytest]
addopts = --strict-markers
markers =
    smoke: 库存关键路径快速检查
    integration: 接口与展示组合检查
    release: 最终制品验收

# 终端命令，按所需门禁分别执行
python -m pytest tests -m smoke --junitxml=reports/smoke.xml
python -m pytest tests -m "smoke or integration" --junitxml=reports/main.xml
python -m pytest tests --junitxml=reports/daily.xml

marker 和目录筛选会同时生效。pytest tests/smoke -m integration 若目录内没有相应标记，可能没有收集到测试。pytest 无测试收集的退出码也非成功，应在门禁中保留，不能用 || true 把它吞掉。

快速集应包含关键边界，例如在站 18、锁定 4、保留 3 得 11；在站 2、锁定 1、保留 3 得 0。Daily 不一定排除 smoke，完整回归常包含快速集。测试金字塔按测试层级划分，与 MR/Daily 这种运行时机划分是两个维度。

GitLab CI 核心

.gitlab-ci.yml 与业务代码一起版本化，Runner 按配置执行命令。共享与私有 Runner 的选择影响网络、隔离和凭证范围。Docker executor 提供较统一的工具环境，但若启用高权限或挂载宿主敏感目录，容器不能被当作充分安全边界。

关键字作用常见误读
stages定义默认阶段屏障不保证每个阶段只有一个 Job
script运行命令并使用退出码输出 PASS 文本不等于退出 0
rules按事件和条件纳入 Job顺序会影响最终匹配
cache复用依赖等可丢数据不作为正式包传递契约
artifacts保存报告和产物应设置保留与访问政策
needs明确依赖与可选产物传递被依赖 Job 也要存在于当前流水线

needs 可以缩短关键路径，但要与 rules 一起检查。如果 release Job 总是存在，而它依赖的 build Job 只在 MR 出现，tag 流水线可能配置无效。可按业务调整条件，必要时采用明确的 optional 依赖，但不能为了消除配置报错就让必须构建变成可选。

受保护变量和环境审批应由项目政策配置。来自不可信分支的流水线不应获得生产凭证，Agent 修改 YAML 也必须经过审查。

标准流水线

下面是仅验证与打包的最小教学流水线。练习仓库需提供 requirements-dev.txt、tests 和 bike_dispatch 包；不把这些路径描述成本仓库已有文件。此配置没有部署步骤。

GitLab CI 教学配置；依赖中应包含 pytest 和 build，镜像生产使用时应固定摘要
image: python:3.12-slim
stages: [check, test, package]
variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"
cache:
  key:
    files: [requirements-dev.txt]
  paths: [.cache/pip/]
before_script:
  - python -m pip install -r requirements-dev.txt

syntax:
  stage: check
  script:
    - python -m compileall -q bike_dispatch

stock_tests:
  stage: test
  needs: [syntax]
  script:
    - mkdir -p reports
    - python -m pytest tests --junitxml=reports/all.xml
  artifacts:
    when: always
    reports:
      junit: reports/all.xml
    paths: [reports/]

package:
  stage: package
  needs: [stock_tests]
  script:
    - python -m build
  artifacts:
    paths: [dist/]

compileall 检查语法，不检查业务公式或类型。stock_tests 失败会阻止 package，when: always 则尽量保留已生成报告。若依赖安装阶段就失败，JUnit 文件不会凭空出现，需要看安装日志。

缓存依赖下载而不是整个虚拟环境，能减少环境路径和解释器变化造成的问题；缓存 miss 仍必须能完整构建。严格复现还需锁定依赖与镜像摘要。构建出的 wheel 或镜像应绑定提交与内容哈希，后续环境部署同一产物，不能每个环境重新拉依赖构建。

多门禁实战

多门禁要先定义事件，再确定检查集合。下面片段展示 MR、定时与 tag 的选择，不包含完整的安装和制品验收环境，需要与公共配置合并。

触发条件片段：实际发布测试应安装并检查指定不可变制品，另配报告归档
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
    - if: '$CI_COMMIT_TAG'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

mr_inventory:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  script:
    - python -m pytest tests -m smoke --junitxml=reports/mr.xml

nightly_inventory:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
  script:
    - python -m pytest tests --junitxml=reports/nightly.xml

tag_acceptance:
  rules:
    - if: '$CI_COMMIT_TAG'
  script:
    - python -m pytest tests -m release --junitxml=reports/release.xml

主干关键回归可以增加单独 Job，覆盖接口与显示组合。构造事件矩阵检查哪些 Job 被纳入，防止 push 与 MR 同时创建重复流水线，也防止 tag 因错误 rules 跳过验收。

断言失败让 pytest 返回非零，Runner 将 Job 标记失败，是否阻止 MR 还取决于项目合并政策和 allow_failure 配置。[2] 若脚本通过管道交给 tee，应检查 shell 是否传播前段失败，不能只拿最后一个命令的退出码。

特色知识点

优化先看关键路径，再看缓存命中和 Runner 等待。拆并行 Job 可以缩短测试时间，但会重复安装依赖并增加资源消耗。可共享构建镜像或依赖缓存，仍需保证缓存丢失不影响正确性。

正式产物用提交与内容摘要标识。latest 可作为方便的别名，但不能作为唯一审计依据，也不应在回滚时只凭它寻找历史包。发布记录保存源码、依赖、产物、验证和审批的对应关系。

流水线变更影响所有后续验收，应像代码一样评审。紧急发布可有受控例外，不能静默删除检查。[1] 交叉编译或特定硬件测试涉及额外工具链，本章库存 Web 服务案例不需要加入这些复杂度。

数据类型丢失后影响正确用途
Cache重装依赖、构建变慢可重建的加速数据
Artifacts证据或包无法交接报告、正式构建产物
制品仓库长期发布和回滚受影响受权限与保留政策管理的版本产物

排查与优化

先确认任务有没有被创建，再看谁在执行和失败在哪一层。不要在没有流水线记录时直接修改库存业务函数。

层检查对象可观察证据
事件与选择MR、schedule、tag 及 rules流水线列表、事件变量、配置校验
调度Runner 标签、在线状态与容量pending 原因、排队时间
环境镜像、依赖、工作目录安装日志、解释器与路径
测试收集、marker、断言用例数、失败栈、JUnit
外部资源规程库、制品库、网络超时类型与服务状态
凭证范围保护规则和有效性权限拒绝码，不打印秘密值

优化时区分等待、安装、执行和归档。若总耗时大半在 Runner 排队，增加 pytest 并行没有解决主要问题；若单个测试等待外部服务，应使用可控替身或专用集成环境。

只对明确的基础设施临时故障重试，并保存第一次失败。稳定断言失败不应靠自动重跑变绿。超时上限也要按 Job 和整条流水线分别设置，取消时确认测试子进程与外部资源得到清理。

Jenkins 与工具

Jenkins 采用 controller 与 agent 分工，Jenkinsfile 可以用声明式 Pipeline 描述阶段与命令。与 GitLab CI 一样，关键问题是执行环境、凭证范围、产物和失败传播，而非只记语法名称。

pytest 运行行为测试，静态分析工具检查部分代码质量，制品仓库保存版本包，Docker 提供可复用环境。工具组合不能替代业务验收：扫描器未报错，不代表 reserve 被正确扣除。选择时优先接现有平台，不为本案例再搭第二套 CI。

若将 Agent 接到 Jenkins 或 GitLab 日志，给它只读、限定任务范围的访问。允许它提交修复分支，不等于允许它修改保护策略、导出凭证或关闭失败门禁。

延伸对照：持续交付的成熟体系

持续交付体系提供了可靠验证与产物追踪的基础。Agent 参与修改以后，新增的是非确定候选的生成方式，已有的分层测试与审批仍然适用。

从持续集成到部署流水线

Fowler 的持续集成写作强调频繁集成并自动验证，Continuous Delivery 讨论从提交到发布的部署流水线。对库存功能，较小改动有助于把失败定位到函数、接口或显示；一次重写整个调度模块则会放大评审和回滚难度。

度量：DORA

DORA 的经典度量包括部署频率、变更前置时间、变更失败率和恢复相关指标，具体名称与口径应随所采用版本注明。它们用于观察交付速度与稳定性，不是某次测试的成功分数，也不能仅靠一条 YAML 就自动改善。

可以记录库存修订从提出到验证的时间、发布后是否回滚以及恢复用时，但要区分等待审批、排队和真正执行。更频繁发布若同时提高故障率，需要回查门禁与变更粒度。

测试金字塔与分支策略

实践维度如何用于本案例常见混淆
测试层级函数、接口、端到端不等同 MR、Daily 时间划分
分支协作小步 MR 与明确合并政策分支名本身不提供门禁
制品流转同一包经验证后发布不是每个环境重新打包
反馈回路失败证据进入 Agent 下一轮不允许 Agent 修改标准来过关

参考：持续集成、Continuous Delivery、DORA、GitLab CI、pytest。

动手验证

先在隔离练习目录执行本地测试，再用平台配置校验工具检查 YAML。不要把本页片段未经补齐直接当作生产发布配置。

练习一：本地跑通多门禁

编写包含 18、4、3 与 2、1、3 的测试，并分别标记 smoke 与 integration。用 --collect-only 检查选中了哪些用例，再运行 marker 命令。故意拼错 marker，确认 strict-markers 报错；用一个不存在的筛选条件，确认零用例不会被记录成验证通过。

练习二：读懂并改写 yml

为 MR、主干 push、schedule 和 tag 画四行事件矩阵，标注应出现的 Job 和依赖。逐条核对 rules，检查是否有不存在的 needs。把 stock_tests 设置失败，预期 package 不执行而失败报告仍归档。平台未运行时，只能称配置推演，不能声称已有绿色流水线。

练习三：本地模拟流水线

本地按语法检查、测试、打包三步顺序运行，故意让测试失败，确认脚本停止而不产出新的正式包。记录每步命令、返回码和候选摘要。若使用仓库 mini-pipeline 模拟器，先读其支持的参数与阶段，不能将模拟输出当作真实 GitLab Runner 行为。

练习四：写一条故障排查记录

推演一条故障：MR 处于 pending，没有 pytest 日志。先查 Runner 标签与可用性，再查容量；只有 Job 真正启动且到达测试命令后，才调查断言。另一条故障是零用例退出，检查目录、marker 与发现规则。给每项写证据和下一检查，不填未经观察的结论。

回顾与自测

CI 将同一版本的检查变成团队可复核的记录，交付则要求产物、证据和审批一致。Agent 可以依据失败修复代码，但不应自行降低成功标准。

绿色流水线自动等于 MR 不能绕过吗？

不等于。合并保护、允许失败、手动例外和权限配置共同决定门禁，必须独立核对项目政策。

Daily 是否应排除 MR 的 smoke 用例？

没有这种要求。完整回归常包含快速集，两者可能重叠；要按风险与耗时定义集合，不把运行时机误当测试层级。

Cache 可否保存唯一正式包？

不应。缓存可丢且缺少可靠交付语义，正式包需要制品与内容标识，并保留相应验证回执。
