两种 Harness，不要混在一起

工程师请编码 Agent 做一个“浮标资料台”，要验证的是窗口、导入、索引、重启和测试；用户在资料台里问设备维护要求，要验证的则是检索、依据、权限和流式结果。两者都被称为 Harness，却包围不同执行对象，不能把开发流程的测试通过当成业务回答质量通过。

六个 Electron 项目展示应用逐步成长时的工作约束，三套 PIV 示例展示编码任务的闭环，Ragent 则提供实际业务平台的分层入口。本文重新构造海洋观测资料场景，功能结构按原项目说明，课程评分与演示结果只作为来源记录，不作为本次重跑证据。1

六项目逐项读懂

以下每项都以新的资料台任务说明如何验收，具体 starter 与 solution 能力以各项目目录为界。

P01 · 把模糊请求变成验收清单

把“做一个好用的资料助手”改成可检验条件：窗口能启动，左侧列出导入资料，右侧有问答区域，应用创建指定本地数据目录。AGENTS.md 提供工作约束，feature_list.json 固定检查项，初始化脚本和进度记录使下一轮可继续。

教学反例是窗口和输入框都出现了，数据目录却硬编码到临时路径，退出后丢失。此时界面看似完成，四项验收仍未满足。比较 starter 与 solution 时不能让前者直接读取后者实现，否则测到的是答案泄漏。

P02 · 会话换人，事实不能跟着丢

新资料“B17 温度探头维护说明”通过文件选择进入主进程，再由服务层保存元数据和正文。preload / IPC 暴露受限请求，页面不应获得任意文件访问权。项目使用 documents-meta.json 等路径承载元数据，可从这些写入点追踪持久化。

会话 A 实现导入，会话 B 只凭交接文件继续做恢复。验收先导入两份不同名称资料，关闭应用再启动，确认 ID、名称与详情都能匹配，不能只看列表还剩两个条目。若正文路径丢失，列表恢复仍只是部分成功。

P03 · 一个功能一个闭环

把一份 1,260 字符的教学维护文档按段落分成若干块，索引统计应解释原文、片段和引用的对应。课程约 500 字符的规模用于教学，实际分块应考虑标题、表格和跨段说明，不能机械认定某个长度最优。

问“空值怎样标记”时，答案引用必须指向实际包含空值规则的块，且摘录与正文一致。只有“索引完成”图标而没有可复查 chunk，不能证明入库成功。交接应分别记已完成分块、尚未验证引用与重建方式。

P04 · 先让故障可见，再修故障

项目 starter 在长文档分块路径设置缺陷，超过特定长度可能得到无效块。用新样本测试：短的设备简介正常，包含多段标定表的长说明却问不出内容。沿原文字数、有效段落、非空块数、索引写入数和召回结果逐级找证据。

如果日志显示解析有 1,800 字符而索引中没有非空片段，应先查分块与写入，改变模型温度无助于补回缺失索引。修复后用同一长文档、边界长度和空段落重测，结构化日志要能关联同一次导入，而非混看上一次成功记录。

P05 · 三个角色是否真的改善交付

平行方案共同实现对话历史，可用新任务检查：先问 B17 的字段单位，再追问“刚才那条引用来自哪里”，关闭重开后仍能查看原对话。单角色自己计划与检查，gen-eval 把实现与评价分离，plan-gen-eval 另加计划与 sprint contract。

材料记录的 1.6、3.3、4.9 属于各方案 rubric，不是“增加角色必然提高质量”的普遍结论。需控制模型、上下文、预算和题目，尤其让评价者依据可重放用户路径而非生成者自述。真正的独立复核应能发现故意漏掉的重启恢复。

P06 · 产品已经存在，强化的是工作系统

此阶段 starter 已有不少业务功能，新增重点是验收清单、交接、基准与清理机制。新任务可要求“另一个工程师仅凭仓库恢复资料台、重跑入库与问答检查”，从可接手性而非新增按钮数量评价。

基准脚本与清理扫描器以 solution 的实际文件为准，不把文档里出现过的命令当成 starter 必然可用。清理也要只报告或删除明确生成物，不能把用户导入资料和未提交改动当成垃圾。质量记录应连到命令、输入和产物，分数本身不足以复查。

三套 PIV 示例，各自多了什么

示例业务执行边界可学的开发契约
01-simple_harnes_demo小型 Python 应用规则、计划、实现报告和验证命令一致
02-rag-harness-demo固定分块、TF-IDF 与模板回答，FastAPI 提供页面编辑提示与停止前检查，mock 保留离线测试
harness-engineering-demo现有 Schedulr 应用，FastAPI / Next.js / Postgres按需上下文、分阶段工作流、代码导航和跨会话推进

这里是三个不同业务载体，不应假装都已经是海洋系统。迁移到资料台时借鉴的是契约与验证方法，而不是把表名或项目名批量替换。

RAG 示例的正确升级方式

用教学维护说明检索出两段内容后，模板生成器能直接拼接，不代表已经调用 LLM。升级时把生成器作为边界替换，保留可注入 client、空命中处理和来源结构。测试应断言证据确实进入请求、空证据不会触发编造式回答、异常能被标为失败。

假 client 可以返回固定的带引用草稿，以验证装配与解析；真实模型评测另看事实支持和语言质量。若只断言结果非空，即使把系统错误堆栈当答案也可能通过，检查项必须与产品行为相关。

Ralph：一个会话不够，就交接给下一个

Ralph 通过反复启动新会话维持长任务，磁盘上的规格、计划与报告承担连续性。教学终止标记如 DONE.txt 是协议，需与验收结果绑定，不能让模型先写标记就跳过测试。

相关驱动可能提交代码并跳过交互确认，不能在重要工作区直接试跑。本章仅解释，不执行这些入口。worktree 隔开文件仍可能共用 Postgres，数据库隔离和清理属于独立选项。自动 Stop 与手动完整 validate 的覆盖范围也应分别核对，不把说明中的期望合并成已运行事实。

Ragent：从教学 RAG 到业务平台

Ragent 的 Java / React 分层覆盖了模型适配、请求编排、知识入库和管理界面。framework 提供通用约定，infra-ai 连接模型和流式协议，bootstrap 编排业务，mcp-server 提供工具服务，frontend 呈现聊天与管理。模块名称描述职责，不自动构成可用性或安全认证。

先有入库链路，后有问答链路

把一份“波高仪维护手册”上传后，需要解析、转换、分块、嵌入和写入等处理才能检索。每个节点与整体任务都要记录状态。用户看到上传成功时，如果向量写入还没结束，应显示处理中，不能直接标为可检索。

假设文档 V2 有 6 块，写入到第 4 块时失败，重试要避免重复和 V1/V2 混合。可用批次与文档版本关联片段，全部就绪后切换可见状态。是否采用这项策略需读具体实现，本段是入库一致性的检查要求，不声称源码已满足所有条件。

问答主线：按本地 StreamChatPipeline

一句“那怎么申请？”发生了什么

新教学对话先问“B17 探头重新标定后，结果如何登记”，再追问“那怎么申请复核”。代词需要依赖当前会话补全，不能脱离历史直接查任意流程。本场景说明流水线功能，不使用项目原问答案例。

  1. 服务创建任务与流式回调，经过队列和 Trace 范围。用户、会话与任务标识应一直可关联。

  2. 加载历史后改写追问，必要时拆成登记规则与复核流程两问。若设备或主体不明，先澄清而非猜库。

  3. 知识路径并行调用启用召回通道，再按配置去重、融合与重排。引用保留文档版本、片段和权限范围。

  4. 证据为空则说明未找到依据，有证据才组装 KB、MCP、历史与当前问题。工具返回的文字仍属于数据，不应作为更高优先级指令。

  5. 增量结果经回调进入 SSE，取消按任务 ID 找到对应运行。界面应区分生成中、取消和完整结束，半段草稿不能保存成最终已验证答案。

容错不是“所有失败都没有影响”

MultiChannelRetrievalEngine 对单通道异常返回空结果，后处理失败可记日志后跳过，改善部分故障下的继续能力。但空结果的原因应能追查：真实无命中与服务失败都显示为空，容易误导后续诊断。

等待 futures 完成不等于已经具有统一超时。慢通道仍可能拉长关键路径，需查看 deadline、取消和线程池配置，不能只因写了并行就承诺低延迟。模型健康、降级、首包探测与 MCP 注册也要在相应实现中逐项核对，README 的平台定位不代替压测和安全审查。

纸上比较时先确定验证对象是编码交付还是在线业务。前者看用户路径与测试，后者还需真实证据、权限与输出语义，不能用同一张“完成清单”混算。2
