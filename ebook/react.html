先分清谁在行动

调度员提出一项具体任务：青禾站目标补到 15 辆，现有可借车数需重新读取；从柳川站补车，但不能超过运输车剩余容量。这个任务的后一步依赖前一步。若青禾站有 6 辆，缺口是 9；若运输车只剩 5 个车位，本次就只能提出搬运 5 辆的建议。还必须确认柳川站扣除保留量后确实有足够可调车辆。

ReAct 将任务表示成一连串可交互的决策。模型选下一动作，宿主运行对应工具，观察进入后续输入。这里的优势是可以在读到新状态后改变做法：若柳川站可调量为零，就停止推荐该来源站，而非继续执行已经失去前提的计划。

本章使用文本协议，Action 指向工具名，Action Input 携带输入，Observation 由程序填写。Thought 可以保留一行简短行动说明，便于阅读日志，但它不是内部计算的透明记录。[1] 审核搬运建议时，可信证据是库存、容量和约束检查结果，不能因为某段说明听起来合理就判定调度安全。

文本协议适合观察解析过程，也更容易出错。工具名被加粗、参数跨行、最终答案提前出现，都可能改变分支。真实系统可以换用结构化请求，ReAct 的反馈循环仍然成立。协议形式与决策模式是两件事。

走完一次循环

以下轨迹来自预设数据和固定回复，展示理想控制流，不是远程模型日志。目标只生成搬运建议，不创建工单，也不锁车。

每次行动

同一问题在另一快照下可能需要另一条路径。若柳川可调量只有 2，即便运输车有 5 个空位，建议量也只能为 2。观察的意义是更新决策前提，不只是让最终文本附上一段工具输出。

为什么结果必须写回历史？

下一次模型请求不会自动继承上一次执行的局部变量。宿主必须把青禾库存、柳川可调量和快照标识放回输入。若只记录“库存查询成功”，数值没有进入提示词，模型无法据此计算缺口。

原项目的 history 是单次函数调用中的轨迹列表，每轮由 build_prompt 重新组装。它并未更新模型权重，也不自动保存到磁盘。为了控制长度，可以把工具结果保留为紧凑字段，但不能把单位、站点编码和采集时间删掉。离开这些上下文，数字 8 无法说明它是可借数、可调数还是车辆容量。

读懂核心源码

源码入口仍是 agent/loop.py，阅读重点为解析、执行优先级和结束判据。下面重新写一个字典化控制流与离线适配器，让每个分支都能被断言覆盖；它不是仓库函数的逐字复制。

第一步：拼提示词，再解析行动

每轮把原始任务和历史交给模型适配器。解析器只接受一个动作，尽早拒绝同轮多个工具请求，避免执行一半以后才发现消息不合法。

教学代码，可离线检查；不连接业务服务
def parse_reply(text):
    lines = [line.strip() for line in text.splitlines() if line.strip()]
    actions = [s.removeprefix("Action:").strip()
               for s in lines if s.startswith("Action:")]
    inputs = [s.removeprefix("Action Input:").strip()
              for s in lines if s.startswith("Action Input:")]
    if len(actions) == len(inputs) == 1:
        return "tool", (actions[0], inputs[0])
    if not actions and text.startswith("Final Answer:"):
        return "final", text.removeprefix("Final Answer:").strip()
    return "invalid", None

这里允许行首空白，但不支持多行参数。程序应明确这些限制，并将非法格式作为可修正的观察反馈；不要把缺失参数默认为一个可能有副作用的值。

第二步：先执行合法工具

执行时按名字查白名单，并把实际返回值追加到轨迹。调用成功之后立即进入下一轮，不接受同一响应里尚未读到结果就写出的结论。

教学代码，可离线检查；不连接业务服务
def run_requested(payload, tools):
    name, value = payload
    if name not in tools:
        return {"action": name, "input": value,
                "observation": "ERROR unknown_tool"}
    try:
        result = tools[name](value)
    except (ValueError, TimeoutError) as exc:
        result = "ERROR " + type(exc).__name__
    return {"action": name, "input": value, "observation": result}

这里只捕获预期的业务输入错误和超时。编程错误应该让测试暴露，不能统一伪装成“工具暂时不可用”。读取结果之后有一次新的决策机会，修正参数是否值得重试还要受剩余预算约束。

第三步：返回答案，或写入错误观察

结束分支需要区分回答完成、格式失败和预算耗尽。返回最后一段文本会把这几种状态混在一起。

教学代码，可离线检查；不连接业务服务
def decide(kind, payload, history, require_evidence=True):
    if kind == "final":
        ok = any(not str(h["observation"]).startswith("ERROR") for h in history)
        if require_evidence and not ok:
            return None, "ERROR evidence_required"
        return {"status": "answered", "answer": payload}, None
    return None, "ERROR invalid_reply"

仓库原实现先判断合法工具，再判断 Final Answer:，最后写无效行动观察；上面为库存任务额外加了证据门槛。这个门槛仍只证明至少一次成功观察，不能证明所有约束都已验证。完整业务应检查必需工具集合和数值关系。

展开本页新编的完整离线循环
可组合代码：依赖本节前三段函数；model 是注入的普通 Python 可调用对象
def cycle(question, tools, model, max_steps=4):
    history = []
    for step in range(max_steps):
        text = model(question, list(history))
        kind, payload = parse_reply(text)
        if kind == "tool":
            history.append(run_requested(payload, tools))
            continue
        final, error = decide(kind, payload, history)
        if final is not None:
            return {**final, "steps": step + 1, "history": history}
        history.append({"action": "protocol", "input": text,
                        "observation": error})
    return {"status": "budget_exhausted", "steps": max_steps, "history": history}

本页函数为测试返回整个结果对象，便于断言退出原因。真实接口适配层还需限制输入输出长度，并保证工具执行超时能够传播取消；单纯在模型外面多套一层 for 不会让阻塞的函数自动停止。

边界与失效方式

离线轨迹能检查状态转移，但不能替代网络故障和副作用测试。接入真实站点平台前，可以逐一检查以下四个断点。

步数上限不等于超时

四轮预算包含最终作答。如果前三轮都在读数据，只有一轮生成答案；第四轮又请求工具，就没有剩余轮次确认结果。与轮次分别设置的还有模型调用超时、工具超时和整个任务截止时间。[2] 被卡住的第二轮不会因为设置四轮上限而自行结束。

需要传递剩余时间而非每轮重新给完整超时。否则三个依赖各等 20 秒，任务可能耗费一分钟，远超入口设定的等待预期。

错误字符串不等于异常处理

ERROR unknown_tool 是协议内的反馈值，Python 的 ConnectionError 则是异常。只有明确捕获并转换的异常才能进入下一轮。源码里的某个工具自行处理错误，不代表主循环替所有工具实现了相同机制。

错误码最好区分可重试和不可重试。站点不存在时反复查询没有帮助；临时限流可按截止时间退避；权限撤销应停止并交给用户处理，而非让模型寻找绕路工具。

工具白名单不等于完整安全边界

即使只注册 calculator，输入也可能触发资源耗尽。对站点工具来说，白名单限制了可调用的函数名字，却没有限制可以查询的区域，也没有防止一次读取全市敏感数据。还需控制输入长度、租户范围、返回规模和执行时间。

本章的教学工具没有写能力。若换成创建搬运工单，重复动作可能造成多张工单，重试前需要幂等标识和审批记录，不能将读取工具的恢复策略直接套用。

能给出答案，不代表任务已被验证

回答中有 5 辆，并不说明选择正确。它可能忽略来源站保留量，也可能把一小时前的容量当成现在可用。业务验证可以检查 move <= deficit、move <= source_surplus 和 move <= capacity，并要求这些值来自允许时间范围内的快照。

单有成功工具观察也可能缺一项证据。本页 decide 是演示性门槛，真正上线的验证器应按任务类型检查必需字段，不能把其简化判断视为完整验收。

动手验证

先运行固定回复，观察历史内容，再考虑真实模型能否稳定遵守协议。离线成功与在线成功应分别记录。

练习一：不联网，验证三轮轨迹

把前面四段函数保存到任意练习文件，再接上这段代码。每个工具返回教学字符串，所有计算由预设数据说明，不访问城市服务。

教学代码，可离线检查；不连接业务服务
tools = {
    "station_snapshot": lambda value: "QH-07 borrowable=6; LC-02 movable=8; fixture=s1",
    "van_capacity": lambda value: "VAN-3 free=5; fixture=v1",
}
replies = iter([
    "Action: station_snapshot\nAction Input: QH-07,LC-02",
    "Action: van_capacity\nAction Input: VAN-3",
    "Final Answer: 建议搬运 min(15-6,8,5)=5 辆；尚未创建工单。",
])
observed = []
def scripted(question, history):
    observed.append(history)
    return next(replies)
result = cycle("给青禾站补车建议", tools, scripted)
assert result["status"] == "answered" and result["steps"] == 3
assert "movable=8" in observed[1][0]["observation"]
assert "free=5" in observed[2][1]["observation"]
assert len(result["history"]) == 2
limited = cycle("预算测试", {}, lambda *a: "Final Answer: 已完成", max_steps=1)
assert limited["status"] == "budget_exhausted"

将 max_steps 改为 2 时，前两个工具仍成功，但任务状态应为预算耗尽。再把工具名改成未登记的名称，第二轮应能看到错误观察。不要靠最后一行固定打印来宣称检查通过，应当让断言检查具体的历史和退出状态。

观察日志时，只问这三个问题

检查请求是否指向正确站点，检查观察是否进入下一轮，检查停止状态是否与实际完成情况一致。若工具成功但最终答案缺失，应记录未完成；若答案先出现而没有所需证据，应记录证据不足。真实日志应隐藏用户身份和密钥，保留足够的站点与版本信息用于复查。

回顾与自测

ReAct 对调度任务有用的地方，是每次库存或容量读取之后可以重新决定。循环的可靠性取决于解析是否明确、执行是否受控，以及观察是否真实回流。

同一条响应包含调用和最终答案，怎样处理？

先消费合法调用，完成后进入下一轮。这个答案是在看到本次观察之前生成的，不应用它宣称本次查询已验证。实际行为仍取决于解析器优先级，应写测试固定下来。

两次工具成功为什么还可能是失败任务？

缺少最终生成轮次、未读到全部必需证据，或约束验证不通过，都应让任务保持未完成。工具成功只是局部状态。

历史记录里写了已搬运，可以当作操作凭据吗？

不可以。建议生成与工单创建是不同动作，只有写工具的实际返回和业务回执才能证明操作发生，本章没有创建工单。

本页以 d9e02cb 快照中的循环与解析入口作对照，另写了公共自行车任务和可组合的离线代码。这里的函数名只属于教学实现，不声称仓库已经提供同名接口。没有运行远程模型。
