人成了瓶颈

夜间有一批维护工单需要补齐规程引用。单次 Agent 可以处理一项，值班员若要逐条启动、看结果再催下一项，就成为队列调度者。自动化可以接管这些重复决定，但不能把“都处理好”当成没有边界的目标。

给每项工单定义状态以后，系统能认领待处理项，读取证据，生成建议，再由验证器判定通过、需修订或等待人工。新一轮由状态变化驱动，不需要人发送“继续”。人的职责转向目标、资源和异常政策：允许处理哪些工单，什么算合格，何时必须停下来。

有些工作本来只需要一次查询，添加外循环会增加延迟与费用。遇到缺少规程、等待维修员确认或权限不足时，继续生成更多文字也没有帮助。Loop 应能进入 blocked 或 waiting，而不是把所有非成功都解释成再试一次。

本章将 Loop 作为工程组织方式，而非具有唯一标准定义的产品类别。所有夜间工单与吞吐数值都是教学设定，未启动实际无人值守任务。

四层能力栈

四层可以用同一项“补齐工单证据”说明。它们并非必然的历史替代关系，而是不同范围的职责。

Prompt、Context、Harness、Loop

用三个不同请求区分工作范围。问“解释工单中 pending 的含义”，可用给定字段定义直接回答；问“BIKE-031 当前维修进度”，需要读取最新工单；要求“把本批 80 项工单补齐引用并形成待审清单”，则需要任务持久化、失败隔离和可恢复执行。

请求需要补的能力不能据此省略
字段解释明确提示和定义事实来源核对
当前进度上下文读取与版本权限和时效
批量补证据执行环境与状态队列逐项验证
持续处理至可审阅外层调度与停机总预算及异常交接

时间长不一定意味着上下文会满，短任务也可能产生很大的工具输出。应按实际 token、任务状态和外部等待判断是否需要压缩与恢复，而不是用固定分钟数推断失效。

内层工具循环决定当前工单下一动作，外层任务循环决定接下来处理哪项工单。它们有不同预算和终止原因。将二者混在一个无限 while 中，会让一项困难工单耗尽整批预算，也不利于重启后恢复。

Loop 的三个零件

一个可运行的契约要描述启动、行动和结束。以合成工单队列为例，触发可来自新批次入队；行动是为一项工单收集证据并生成候选；停止条件是所有允许项都已得到验证状态，或触发了外部上限；模型说“好了”不算验证。

零件教学契约具体判据
Trigger批次 batch-7 被标为 ready版本未处理且当前无有效租约
Action处理一个未完成工单保存来源、候选和验证结果
Stop Condition完成或暂停整批无 pending/running 项，或预算/截止时间/人工阻断

完成目标可以定义为每项工单包含有效规程引用、故障分类和不超权限的建议；无证据项则明确标记 needs_review。是否把 needs_review 视为批处理完成，应在任务契约中约定。对“全部自动通过”的目标，缺证据项意味着未达成，不能偷偷改变成功定义。

外循环还应有失败分类。输入缺失可等待，参数错误可修正，权限拒绝应阻断，临时网络错误才适合有限重试。把不同失败都交给模型重新写一次，会烧掉预算却不改变外部条件。

Loop 不是 Cron

Cron 可以作为触发器，但不会替任务定义成功和恢复。反过来，Cron 启动的脚本也完全可以包含决策与状态机，所以二者并不互斥。区别在于系统是否根据证据选择行动，以及是否保存可恢复状态。

Cron

触发事件固定工作仍需处理
02:00 到时启动维护批次扫描重复启动、上轮未完、时区变化

如果上轮任务仍在运行，下一次触发应合并、跳过或排队，不能默认再开一份。使用批次 ID 和租约区分同一业务任务的重复触发。

Loop = Cron + 决策体

当前状态调度决策依据
pending 且预算够认领一项并执行依赖齐备
waiting for manual停止轮询并等待事件缺审批，模型重试无效
全部 verified完成批次验证回执齐全
预算耗尽暂停并交接未完成项明确保留

“每轮重置模型上下文”可以防止历史不断堆积，但前提是磁盘工件足以恢复目标、失败和版本。重置而不持久化会导致重复劳动。保留完整会话也不保证连续性，关键是实际状态与下一轮输入相符。

从 ReAct 到目标驱动自主系统，具体实现差异很大。不能仅凭产品名断言某工具采用固定指令、独立检查或重置上下文；应读运行配置和轨迹。本页讨论的是可选择的设计，不把它写成所有编码代理的共同事实。

一个认真 Loop 的零件

外循环越长，越需要将执行资源和业务状态分开。队列、租约、隔离工作区、证据存储与验证器共同决定恢复是否可靠。

部件本案例用途失败边界
隔离工作区并行处理不同报告工件外部工单写入仍需隔离或幂等
技能统一补证据与拒答规则技能版本变化要重评
连接器读取工单和规程凭证过期进入 blocked
Verifier检查引用、分类和范围必须能拒绝空洞完成声明
磁盘状态记录工单版本、回执和租约原子写入避免半份状态
动态工作流按需拆出独立证据任务限制扇出与总成本

检查点应写在可恢复的事务边界。例如先保存候选与验证结果，再把任务改为 verified；若顺序相反，崩溃后可能只看到完成标志而没有证据。重启时对 running 项检查租约和外部回执，避免无条件重做。

动态扇出要满足任务可分、权限可控和结果可合并。一次创建很多角色并不会缩短规程缺失造成的等待。全局预算最好由外层账本统一扣减，防止每个子任务都以为自己还有完整额度。

最重要的一步：验证

验证器把候选转换成可交付状态。对补证据任务，可以先检查来源 ID 是否存在且有效，引用是否支持该处置，故障分类是否满足规则，以及有没有未经批准的写入。不同检查产生独立结果，不只返回一个笼统评分。

实现者与验证者的职责应分开，但不一定需要两个模型。确定测试可检查字段与范围，模型辅助检查复杂语义，人工审核处理无法自动判定的安全条款。另一个模型也可能共享误解，所以独立身份不是充分条件。

失败反馈应指出具体对象。例如“工单 17 引用 T-2，但故障为制动失效，应补 B-4 证据”，比“请改好一些”更能改变下一轮行动。反馈也应限制改动范围，不能让修复一个引用的循环重写整批报告。

目标可自动检查仍需外部判断
引用完整每项有来源 ID、版本和位置证据是否真实适用
报告可读字段齐全、术语一致现场人员能否据此行动
不越权写工具未执行、权限日志特殊应急授权是否合理

对可读性这类主观目标，可事先定义具体维度并由固定评审样本校准。不要每次看到结果后才调整评分，使循环永远有理由继续。达到硬停止条件但质量仍不合格时，应输出未通过，而不是把停止误写为成功。

Orchestration Tax

自动处理一批工单可能几分钟就产生很多建议，人工审查却需要理解证据。协调、审查、合并和异常处置构成 Orchestration Tax，不能仅按模型并行数估算吞吐。

工具能力

生成配置教学产出并行的局限
4 个 worker每小时 40 项候选候选不等于已验收项

人的带宽

审查资源教学能力积压
1 位审核者每小时可靠审核 15 项每小时增加 25 项待审

如果降低人工审查深度来追赶输出，风险会转化为理解债。[2] 后续追查错误时，还要重新读大量没有形成共同理解的产物。

真实吞吐

队列状态可持续吞吐调度动作
候选 40/h，审核 15/h最多约 15/h 完整交付限流或提高自动验证覆盖
验证可自动淘汰无效项以实测通过率计算仍需保留抽查和关键项复核

这些数值只用于容量推演。实际审查复杂度不一致，不能把平均 15 项当成长期固定能力。观察待审队列年龄、关键问题漏检和返工率，比只看创建候选数更能判断系统是否健康。

三种常见形态

形态在维护任务中的使用需要控制
Solo Loop一个执行者配确定验证，先处理低风险项每项预算与验证覆盖
Maker-Checker生成者与语义检查者分离意见分歧如何回到具体证据
Manager + Helpers独立工单或独立证据可并行扇出、结果版本与人工带宽

优先从单项任务的轻量反馈环开始。发现确实存在可并行证据读取，再增加 helpers；发现确定检查覆盖不了语义质量，再增加 checker。角色数量不应成为架构目标。

对于资料整理或报告生成，人类可能愿意每天审核一次；对于实时调度，等待很久会让快照失效。这两种场景的触发、预算和结束定义不同，不能直接照搬别人的长时间无人值守配置。

质量曲线与成本

迭代可能提高质量，也可能在错误评分下退步。应保存最好且已验证的版本，不要默认最后一轮最好。若连续两轮没有新证据或质量改善，应暂停并检查任务是否缺少外部条件。

每轮成本包含生成、检索、自评、反思和协调。设一轮教学成本为 0.02，三轮共 0.06；如果第二轮已通过，固定跑满三轮既浪费费用，也可能引入新错误。若评估调用比生成还贵，先用确定规则过滤明显失败更合适。

硬上限应覆盖轮次、墙钟时间和费用，通常不宜只选其中一个。[1] 轮次控制循环数量，截止时间控制等待，金额控制不可预期的模型用量；外部服务不返回时，还需要可取消调用。

可复用的技能、测试和故障分类能降低下一次任务的重复成本，但必须经过审查再沉淀。一次失败后临时生成的建议可能只适用于某批工单，不能不加范围地升级为永久规则。没有统一的“适合跑几小时”答案，应按进度和风险决定，而非追求通宵运行。

延伸对照：Loop 的学术与工业脉络

Loop 的研究前身涉及行动反馈、反思、自我修订和接口设计。不同工作对反馈真实性有不同假设，迁移时要看原实验条件。

从 ReAct 到自我改进

ReAct 组织行动与观察，Reflexion 把反馈保留到下一尝试，Self-Refine 研究自反馈修订。它们说明反馈可以用于迭代，但自评不保证事实正确。维护任务中，工单版本和规程依据才是外部约束。

目标驱动系统的早期经验也表明，模糊目标与没有进度判据的重复调用容易空转。具体失败仍应按日志分析，不宜将某个产品一概当作无用或先进的代表。

技能与长期记忆

Voyager 使用可复用技能支持持续探索，为“保存已验证方法”提供了研究例子。外部记忆与任务工件则帮助新一轮恢复上下文。对本案例，适合沉淀的是证据校验和工单状态规则，而非某辆车的临时处置结论。

Agent-Computer Interface

SWE-agent 强调 Agent-Computer Interface，工具反馈格式和编辑方式会影响模型完成任务的表现。这提醒我们，下一轮输入不应只是“失败了”，而应提供能定位问题的结构化差异。

研究方向映射到本案例不能直接推出
行动反馈检索条款后修订建议任何观察都可靠
语言反思记住具体失败条件多试必然成功
技能积累复用已验证检查流程自动生成即可永久采用
接口优化提供可定位的错误回执无需业务验证

动手验证

这些练习先写契约和状态推演，不启动后台任务。能说明停止和恢复以后，再接执行器。

练习一：写下你的第一个 Loop 契约

为批次 batch-7 写 Trigger、Action、Stop 三项，补充验证器输入与输出。至少包括 verified、needs_revision、waiting、budget_exhausted 四种结果。测试一个缺规程的工单，下一步应等待或交审，而不是无限改写。

练习二：区分“可检验”和“不可检验”的目标

将“所有工单引用可定位”“报告更专业”“无未处理故障车”“页面体验更好”分别拆解。可定位引用需要 ID、版本和位置；更专业需要事先定义评审维度；无未处理故障车需要真实状态且可能超出助手权限。检查目标是否可观测、可控制，不能只因为能写个数字就认定可验收。

练习三：给自己算一次 Orchestration Tax

用每小时 40 项候选、15 项人工审查算一班 4 小时的积压：若初始为零，理论新增 100 项。再考虑 20% 候选被自动拒绝，进入人工的 32/h 仍高于 15/h。决定降低并行、减少候选或增加可靠验证，而不是要求审核者默认批准。

练习四：审计一次停机原因

给三次停止写回执：完成 20/20、处理 12/20 后预算耗尽、处理 8/20 后等待资料。每次记录剩余任务与恢复条件。只有第一项可称全部完成，后两项虽已停止仍有明确未完成状态。

回顾与自测

Loop 接管的是下一轮的启动决定，不是取消人类责任。目标、证据、预算和恢复路径要在自动化之前确定。

Cron 能否启动一个有决策的 Loop？

可以。Cron 是触发方式，任务体可以读取状态并决策。二者不冲突，关键看是否有持久状态和明确终止规则。

每轮重置上下文会不会丢进度？

如果进度只存在于聊天里就会。重置前必须保存目标版本、产物、失败与回执，下一轮从这些工件恢复。

到达预算上限算任务成功吗？

不算。它是安全停止原因，应列出未完成项和恢复条件，与验证通过分开统计。
