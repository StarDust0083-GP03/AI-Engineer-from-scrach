Agency 来自模型，工程来自 Harness

调度平台新增一条规则：维修锁定车辆和安全保留量不能进入可调库存。模型也许能写出减法，但它需要先找到计算入口、读懂数据单位、修改测试并确认界面没有继续展示旧字段。一个语法正确的函数并不等于功能已经接入。

模型提供理解与生成能力，运行环境提供文件、工具、依赖和反馈。二者共同决定结果。编排也可以帮助模型减少错误，不能把所有能力归于某一个组件；同样，固定工作流并非天然脆弱，业务依赖稳定时，确定流程往往更容易验收。

本章将 Harness 理解为模型执行任务所依赖的工作环境与治理层。它决定什么上下文可见、什么工具可执行、什么状态可恢复，以及什么证据足以结束任务。工具调用只是其中一个接口，关键是执行前后都有可检查的政策。

下面以自行车调度代码改动为新教学案例，保留原仓库 Harness 课程的入口。不修改那些示例工程，也不声称它们已经实现自行车业务。所有测试和状态描述均为设计与教学推演，执行范围以本页标注为准。

harness 的五个子系统

将一次“修改可调数计算”的工作拆成五份工件，能看清每个子系统怎样参与验收。

规则：一张地图，不是百科

规则入口应帮助新会话找到事实和执行命令。适合常驻的是工作范围、禁止操作和完成定义，详细业务背景则链接到专门文档。入口过长会增加成本与维护难度，但“控制在某个固定行数”并不能自动保证有效。

对可调数功能，可以把不变量写成带输入输出的任务契约，让模型和测试共享同一个计算定义。不要只写“正确处理库存”，因为可借、在站和可调可能是三个不同字段。

新编任务契约，非仓库指令原文
功能：返回站点可调数量
输入：present=18，repair_locked=4，reserve=3
期望：movable=11
不变量：movable 不小于 0，不大于 present
范围：只改库存计算、接口映射及相应显示
禁止：生产数据访问、部署、修改认证策略
完成证据：边界测试 + 接口测试 + 展示字段核对

仓库中的规则文件适合检查如何列出命令、约束和按需上下文。版本化文档可以成为团队共同依据，但仓库里也可能有过期说明。若代码、文档和测试冲突，应记录分歧并确认权威来源，不能简单把任一文件当作无误的真相。

越重要的规则越应在执行边界强制实施。禁止部署需要工具账户权限或执行器拦截，不应只靠规则里一句话。业务不变量可以转成测试，文档保留解释与适用范围。

技能：按需加载的工作流

技能把一个任务类型所需的方法组织成可重复调用的工作流。库存计算技能可在实现相关需求时加载，内容包括定位入口、检查单位、补充测试、更新接口契约和保存证据。与所有任务都适用的安全规则相比，这些细节无需每轮常驻。

技能阶段输入产物与停止条件
plan需求、现有实现和测试入口范围、依赖、验收案例；缺事实先确认
implement已确认计划最小改动与局部检查回执
validate候选版本对应版本的完整测试结果
reviewdiff、契约与验证证据问题列表及其影响，不只给好评

技能名称不是平台通用 API。不同工具如何发现与加载文件，应按各自规范配置；本页只说明工作流职责，不新增工具扩展。加载失败、路径失效或文档过期也要可见，不能默默退回一个旧模板。

技能可以沉淀已验证的业务检查，例如“维修数量不可重复扣除”，但不能把某次站点数据或临时异常处理写成永久流程。改动技能后可用已知正确和已知错误案例检查它是否仍能区分。

Hooks：自动触发的质量门

Hook 把检查接到事件边界：调用前做权限与输入验证，编辑后做局部静态检查，结束前检查完成证据。自动触发减少遗漏，但只有所有执行路径都经过该边界、配置受保护且失败能阻断时，才能提供强约束。

结束钩子依赖验证命令的覆盖范围。若命令只编译而不运行测试，绿灯并不能证明可调数算对；若模型能够改掉钩子或用另一入口结束，门禁也可能被绕过。[2]

事件本案例检查阻断依据
工具执行前路径在工作区、无生产凭证读取拒绝越界能力
文件修改后快速语法与类型检查报告局部错误，不冒充全量通过
请求结束时验证回执版本与候选版本一致缺证据或失败不准交付
独立教学门禁函数；不是特定平台 Hook 注册格式
def stop_gate(candidate_digest, receipt):
    if receipt is None:
        return {"allow":False, "reason":"verification_missing"}
    if receipt["digest"] != candidate_digest:
        return {"allow":False, "reason":"verification_stale"}
    if receipt["exit_code"] != 0:
        return {"allow":False, "reason":"verification_failed"}
    return {"allow":True, "reason":"checks_passed"}
assert not stop_gate("new", {"digest":"old", "exit_code":0})["allow"]

相同代码修订后的测试结果才有效。若测试通过后又修改计算函数，旧回执应失效并重跑。编辑后立即运行全量测试有时过于昂贵，可以分为快速反馈与交付门禁，但不能让快速检查的结果冒充完整验收。

PIV 循环：plan → implement → validate

PIV 将计划、实现和验证分开保存，降低长会话里目标漂移的风险。边界清楚不等于阶段永不回退；发现计划前提错误时，应更新计划版本，而非在实现阶段悄悄改任务目标。

20 个 harness 机制

这 20 项保留课程机制顺序，解释全部改为自行车助手的工程用途。每项是可选择的能力，不能因为清单齐全就全部常驻。

课机制新案例中的用途与边界
s01Agent loop读任务、请求工具、写回结果；以结构化状态结束
s02Tool use添加库存读取 handler，公开声明与执行表保持同步
s03Permission汇总角色只读，创建搬运工单另需审批
s04Hooks结束前核对候选版本与测试回执
s05Todo / plan记录函数、接口、显示三处依赖，防止只改一处
s06Subagent让独立检查者只读差异和证据，不共享无限对话
s07Skill loading只有库存任务加载可调数的专用工作流
s08Context compact压缩旧讨论，保留字段单位和未解决问题
s09Memory存已确认的长期报告规则，临时优先级带期限
s10System prompt按身份、任务与权限组装，外部文本不提升优先级
s11Error recovery区分导入失败、断言失败与服务超时，采取不同恢复
s12Task system任务带稳定 ID、依赖和产物，重规划不混用旧编号
s13Background tasks长测试后台运行，完成回执到达前不能宣布通过
s14Cron scheduler定期启动回归，不把一次触发等同于任务完成
s15Agent teams库存与维修独立工作，汇总等待必需产物
s16Team protocols交接包含快照版本、失败码和证据 ID
s17Autonomous agents任务认领带租约，过期恢复防止重复执行
s18Worktree isolation代码目录隔离不替代外部数据库和资源隔离
s19MCP plugin工具服务版本和访问范围受控，不盲信发现结果
s20Comprehensive集成后测试组合行为，尤其取消、恢复与审计

s13 后台与 s14 定时解决的是启动和等待，不直接提高答案质量。s18 隔离代码工作区，也不能防止两个任务同时修改同一远程工单。将这些机制组合时，要给外部副作用分配独立资源或幂等键。

增加机制前可记录基线失败率，加入后再测同类样本；已有机制也应定期做移除实验。[1] 新模型可能不再需要某些提示引导，但权限、审计和业务验收不能仅凭模型更强就删除。

Agent 为什么会失败

失败应定位到缺失的环境能力，而不是笼统归因于模型“不听话”。下面沿用十二讲顺序，用新的症状与检查方法展开。

讲本案例里的失败要查的工件
01函数会算，但接口仍返回旧值端到端数据链
02有工具却没有完成定义任务契约与检查入口
03维护人员口头知道单位，仓库没写字段文档和数据样例
04长指令里埋着库存扣除例外入口索引与按需规范
05换会话后重复修改已完成接口进度账与实际 diff
06依赖未装好，失败被当代码问题初始化回执
07为库存需求改了认证配置范围约束和文件差异
08功能项只有“完成”没有证据状态清单与验证链接
09编译通过就宣布功能可用行为断言与 stop gate
10纯函数正确，页面二次扣除接口到展示集成测试
11某角色重试很多次却无记录完整 trace 与费用账
12留着后台进程和未知测试结果会话收尾与交接回执

巨型规则入口的问题不仅是长度，还包括冲突与权威不清。把同一业务公式在多个文件分别维护，会逐渐产生不同版本；可以给公式指定权威文档，再让测试和代码评审引用它。

“留下干净状态”不意味着删除所有未完成工作。应明确标记未验证改动、后台任务和阻塞，保留可恢复材料。随意清理会损失证据；把半成品写成已完成则会误导下一会话。环境初始化失败时也应保留诊断，不能反复改业务代码试图解决网络或依赖问题。

状态与连续性

长任务的进度应独立于聊天上下文。一个可交接记录包括目标版本、已完成项、产物路径、验证回执、仍在运行的进程与下一项动作。任务 ID 稳定，状态从 pending 到 running、verified 或 blocked，不能仅凭模型一句话切换。

后台测试启动时返回任务 ID，结束后写退出码和日志位置。新会话若看到 running，先检查进程或任务服务，而不是再启动一遍。重试使用同一目标版本，发现代码变更时让旧测试结果失效。

依赖文件与运行时也属于状态。package.json 或 pyproject.toml 描述依赖需求，不一定锁定全部解析结果，还应使用相应锁文件与固定解释器或容器版本。初始化脚本要可重复执行，并避免连接生产服务。

课程里的递进项目能用于比较不同状态机制，但演示成功不能证明恢复正确。可以在写完接口、尚未验证时模拟会话中断，再由新会话只依据工件继续，检查它是否知道哪些结果仍不可信。

权限与安全边界

工具入口是安全边界，文本命令过滤只是其中一层。拦截某个 rm 写法不能覆盖脚本、别名、符号链接或其他语言的删除操作；拒绝名为 .env 的文件也不能阻止凭证出现在其他路径。应通过沙箱、文件系统权限、网络限制和独立账户降低实际能力。

对本案例，工作区可编辑，源码资料只读，生产凭证不可见，部署工具不提供。测试仅使用合成站点数据。路径校验应解析真实路径并处理符号链接，禁止通过工作区里的链接逃到外部目录。

敏感写操作可设计预览与审批两步。预览给出站点、数量、证据和有效期，审批绑定动作摘要；若模型后来更改参数，需要重新获得同意。日志记录谁批准了什么，不保存可重放的完整凭证。

可用性与安全可以同时设计。允许在隔离环境安装锁定依赖，不等于允许任意网络脚本以宿主高权限执行。先列出完成任务必需的能力，再给最小范围，遇到不足时走明确申请，而非让模型寻找绕过方式。

延伸对照：harness 工程的公开脉络

Harness 相关资料包括基准、长期任务实践和工具约定。不同资料强调不同部分，不能将某篇文章的工程观点当作所有任务上的实测结论。

基准与评测

SWE-bench 用真实仓库问题评价修复能力，AgentBench 覆盖多个交互环境。比较结果应同时报告模型、工具接口、上下文预算、验证方法和尝试次数。同一模型采用不同环境可能有明显差异，但具体差异需要按对应实验说明，不能直接推出某个 Hook 必然提升多少。

一线工程写作

长任务工程写作强调初始化、增量推进、状态交接与验收。可用这些建议检查库存功能是否具备可恢复路径。AGENTS.md 和 CLAUDE.md 等文件是上下文约定，不是操作系统权限策略；是否加载、加载顺序与作用域都取决于使用的工具。

对某个早期自主 Agent 的空转，也应按具体运行证据分析。可能是目标不清、工具反馈不足或模型能力限制，不能仅凭产品名称将所有失败归到 Harness。

动手验证

练习在隔离副本中进行，目标是检查环境是否兑现约束。不要在生产代码或凭证目录里用破坏性输入试安全边界。

练习一：跑通最小 PIV 闭环

为教学函数 movable(present,locked,reserve) 写计划与断言。输入 18、4、3 应为 11；输入 2、1、3 应归零。实现后保存局部与集成验证的回执，检查 stop_gate 是否只接受当前候选摘要。原仓库最小 demo 可作为流程对照，但不用它的业务题目代替本案例。

练习二：故意破坏完成标准

故意让函数漏扣 reserve，原本的 18、4、3 用例应失败。再让 Agent 尝试结束，确认门禁返回 verification_failed。随后故意提供旧代码的绿色回执，确认返回 verification_stale。门禁同时要能区分没有运行、运行失败和运行结果过期。

练习三：给五个子系统各写一条

按五个子系统各写一项具体工件：公式权威入口、测试工具、依赖锁、进度记录、验收命令。让另一个没有聊天上下文的会话读这些工件，检查它能否说清任务范围和剩余工作。若还需口头解释，补缺失事实而非堆更多泛泛规范。

练习四：读一个 sXX 课程

挑选 s08、s12 或 s18 的一个机制，明确它解决的当前失败。加入前后使用相同案例比较，记录是否减少上下文丢失、重复任务或文件冲突。若没有可观察收益，先不集成；课程完整清单是学习索引，不是必须安装的配置清单。

回顾与自测

Harness 的验收重点是环境能否把声明变成实际约束。范围、权限和验证应能在模型不配合或会话中断时继续成立。

Stop hook 是否一定无法绕过？

只有相关入口受控、配置不可随意修改且失败能阻断时才有约束力。还需要测试命令本身可信，不能把 Hook 存在当成安全证明。

规则文件写得短就够了吗？

短有利于读取，但还需事实准确、权威清楚、链接有效和完成条件可执行。缺失关键单位的短规则仍然危险。

独立验证者必须是另一个模型吗？

不必。规则、测试、静态检查和人工复核都可以独立验证。另一个模型也可能共享偏差，不能自动代替这些证据。
