从对话到工具调用

谁在执行函数

早高峰前，值班员问公共自行车助手：青禾站现在能调出几辆车？对话模型可以生成一个数量，但站点库存会随借还变化，参数里学过的文本无法证明此刻有多少辆可用车。助手需要读取调度系统，而调度系统的访问能力掌握在应用程序手中。

把职责拆开后，一次查询包含三个不同事件。模型选择 read_station 并给出站点编码；宿主检查编码、身份和查询权限，然后运行函数；模型接收查询结果，组织给值班员看的解释。前一个事件成功，不代表后一个事件已经发生。网络断开时，模型仍可能正常生成调用请求，库存读取却没有完成。

本章用教学站点 QH-07 建立最小样例。固定快照中有 18 辆在站车，4 辆处于维修锁定，另有 3 辆是不可调走的安全保留量，可调数量为 18 - 4 - 3 = 11。这些数字都是离线设定，不是任何城市的实时运营数据。模型应把这个来源边界告诉值班员，不能把演示结果描述成已查询线上平台。

从日志判断动作是否发生，要找到执行开始、执行结束及结果编号。自然语言里的“正在查询”只是输出文本。即使调用请求合法，宿主也可以因为租户不匹配而拒绝执行，之后将拒绝原因作为观察交回模型。权限检查因此不能只写在提示词里。

调用有两条出口

两种出口决定宿主需不需要再次请求模型。把分叉画成消息账本，可以同时检查返回值和调用次数。

读懂 Function Calling 协议

这里沿用 OpenAI Chat Completions 风格的字段，目的是理解消息怎样配对。其他供应商的内容块结构可能不同，接入时应按所用接口文档转换，不应直接复制消息字典。

载体内容必须保持的关系
tools函数说明和参数约束声明的名字要能映射到宿主实现
tool_calls调用编号、函数名、JSON 参数字符串每项必须独立校验
tool 消息本地结果的序列化文本tool_call_id 对应原调用编号
assistant 文本解释及引用数值不超出工具证据
教学接口声明，字段形态参照 Chat Completions；并非仓库现成工具
station_tool = {
    "type": "function",
    "function": {
        "name": "read_station",
        "description": "读取一个公共自行车站点的库存快照，不修改车辆状态。",
        "parameters": {
            "type": "object",
            "properties": {
                "station_id": {"type": "string", "pattern": "^[A-Z]{2}-[0-9]{2}$"}
            },
            "required": ["station_id"],
            "additionalProperties": False
        }
    }
}

arguments 通常是字符串，需要先解析 JSON。parameters 里的类型和必填项帮助模型构造参数，但不能代替宿主的检查。有的服务只支持 JSON Schema 的部分关键字；上面的正则即使没有被服务端强制执行，宿主仍须执行相同的编码规则。

站点存在与否是业务事实，无法靠字符串格式判断。QH-99 可以符合格式，却不在当前租户的站点集合里。权限、库存版本和读取超时也不属于参数形状。宿主应分别返回可识别的失败状态，让调用方区分应修正输入、重新登录，还是稍后重试。工具描述只说明能力；真正开放了哪些能力，还要看执行注册表。

走完一次调用

以下是人为构造的完整消息轨迹，用来审核协议，不声称模型在线产生了这些输出。初始消息是 system 和 user 两项。system 要求库存数字带快照编号，user 询问 QH-07 的可调数量。第一次响应提出 read_station，参数为 {"station_id":"QH-07"}，调用编号为 call-qh-1。

宿主把整条 assistant 请求加入历史，随后从本地固定数据表读到 present=18、repair_locked=4、reserve=3。结果还携带 snapshot_id="sim-0730" 和 mode="fixture"。回填之后，消息列表由两项变成四项：指令、问题、调用请求、工具结果。第二次生成可以说明可调 11 辆，并指出这是教学快照。

如果读取抛出超时，第四项应是失败结果，不能用先前缓存的成功数值偷偷补位。若业务允许缓存，应同时回填数据年龄和缓存标记，让模型能够解释其时效。把成功与失败都表示成结构化结果，有助于测试这两条轨迹是否被混用。

为什么用 tool_call_id 而不是靠顺序？

假设同一次响应还请求读取邻站 LC-02。两个请求可能并行执行，后请求的结果先完成。按列表位置配对就会把柳川站库存装到青禾站名下。编号将结果绑定到具体调用，追加结果时应原样保留；宿主不应重命名编号或将两个结果合并成一条没有对应关系的消息。

还要保留发起调用的 assistant 消息。仅存一段“查询库存”的文本，再追加 tool 结果，会丢失函数名、参数和调用编号。接口可能拒绝这样的消息，也会让离线审计无法重建执行过程。[2]

逐段读源码

原仓库从单文件到模块化工程展示了声明、分发和回填三个位置。本节用同样的接口边界重新写一个站点查询版本，代码标注为教学片段，不把它冒充源码逐字摘录。模型适配器负责返回普通字典，业务函数不依赖某个 SDK。

第一步：组装消息并第一次调用

先只讨论直接返回的出口。reply 是适配器已转好的响应字典。判断工具请求用结构字段，不能在 content 里搜索“调用”两个字。

教学代码，可离线检查；不连接业务服务
def first_turn(question, model_call, tools):
    messages = [
        {"role": "system", "content": "库存回答须注明快照来源；失败时不要猜数。"},
        {"role": "user", "content": question},
    ]
    reply = model_call(messages, tools=tools)
    messages.append(reply)
    if not reply.get("tool_calls"):
        return {"status": "text", "messages": messages,
                "answer": reply.get("content") or ""}
    return {"status": "needs_tools", "messages": messages, "reply": reply}

适配层应移除传输专用字段，并保留接口允许回传的 assistant 字段。空文本不是异常：工具请求响应的正文可以为空。若直接文本包含实时数值，业务层仍可要求额外的证据检查。

第二步：执行工具

执行入口面对模型生成的非可信参数。这里用标准库完成必需检查，示例只读固定数据，不暴露任意 Python 函数。

教学代码，可离线检查；不连接业务服务
import json
import re

def dispatch(name, raw_args):
    if name != "read_station":
        return {"ok": False, "error": "unknown_tool"}
    try:
        args = json.loads(raw_args)
    except (TypeError, ValueError):
        return {"ok": False, "error": "bad_json"}
    if not isinstance(args, dict) or set(args) != {"station_id"}:
        return {"ok": False, "error": "bad_fields"}
    sid = args["station_id"]
    if not isinstance(sid, str) or not re.fullmatch(r"[A-Z]{2}-[0-9]{2}", sid):
        return {"ok": False, "error": "bad_station_id"}
    if sid != "QH-07":
        return {"ok": False, "error": "station_not_in_fixture"}
    return {"ok": True, "station_id": sid, "present": 18,
            "repair_locked": 4, "reserve": 3,
            "snapshot_id": "sim-0730", "mode": "fixture"}

检查顺序先缩小名字，再解析参数，再验证字段集合与值。additionalProperties=False 的约束在这里对应字段集合判断。真实服务还应在查询前绑定认证主体和租户，不能让模型通过参数挑选任意租户。只读示例没有重试写操作带来的重复执行问题。

第三步：写回结果并第二次调用

工具结果以 JSON 文本写入消息，以便模型看到数值字段和失败码。收尾请求明确禁用继续调用；若选用的供应商不支持同样字段，要在适配层实现等价限制。

片段：依赖前面的 dispatch 和返回普通字典的 model_call 适配器
def finish_turn(state, model_call, tools):
    messages = state["messages"]
    for request in state["reply"]["tool_calls"]:
        fn = request["function"]
        result = dispatch(fn["name"], fn["arguments"])
        messages.append({"role": "tool", "tool_call_id": request["id"],
                         "content": json.dumps(result, ensure_ascii=False)})
    final = model_call(messages, tools=tools, tool_choice="none")
    if final.get("tool_calls"):
        raise RuntimeError("final_turn_requested_tool")
    return final.get("content") or ""

一次响应可能携带多个请求，所以上面的 for 不代表只执行一个函数。业务如需“最多一项”，应在任何执行开始前检查列表长度，并对超额请求给出协议允许的失败反馈。第二次生成也必须有超时和空答案处理，否则两轮限制仍可能长时间不结束。

拆成模块后有什么变化

按职责拆分时，可以让 tools/ 保存只读业务函数，注册模块导出声明与处理器，模型适配模块处理 SDK 对象，编排模块处理消息顺序。新增站点工具时先为业务函数写离线断言，再登记接口，最后调整模型何时选择它的说明。

原仓库的模块化目录适合用来核对这些边界，但本页没有把自行车工具写进该目录。不要照着本页的名字去寻找仓库里不存在的 read_station.py；它是新编的教学实现。目录拆分本身也不会增加安全性，只有实际执行的校验才会拒绝危险输入。

边界与常见误解

把协议跑通以后，仍要检查哪些保证来自控制流、哪些只来自语言约定。下面几个边界会直接影响值班员是否能依赖答案。

“一次工具调用”是提示词约定，不是硬限制

“读一次就回答”可以帮助模型选择动作，却无法限制一次响应里包含两项请求。两轮编排限制的是模型请求次数。工具执行次数、单次执行时长以及总费用需要另设计数和截止时间。

最终响应如果还含有调用请求，应当报告无法在预算内完成，而不是把空 content 当作有效答案。能否继续要由宿主决定，不能让模型通过输出“还需要一步”自行扩张权限。

天气工具返回的是模拟数据

原标题对应仓库里采用固定返回值的天气实现。本页用站点库存固定快照承担同样的教学职责：它隔离了网络与认证，使 18 - 4 - 3 的结果可重复核对。[1] 这类替身无法测试调度平台是否延迟更新、是否限流，也不能验证站点现场盘点和平台读数一致。

从固定快照接入真实数据时，返回格式最好增加采集时间、库存版本和来源服务。若调度平台读取失败，就保留失败状态；不能让桩数据在生产配置错误时自动成为兜底库存。

参数校验几乎为零

合法 JSON 可以是列表、数字或空对象。即便是字典，也可能漏字段、传入布尔值代替数量，或者把别的区域编码混入参数。类型校验之后还要做存在性、访问范围与业务约束检查。

拒绝信息应当足够让模型修正输入，但不要把内部堆栈、数据库地址或完整凭证返回给模型。对格式错误和权限拒绝采用不同错误码，有助于避免对永久拒绝反复重试。

消息历史不是长期记忆

四条消息只属于这次查询。函数结束后若没有保存，下一次问“邻站呢”就没有前次站点可供解析。保存消息能支持多轮交互，但库存事实的时效不能随历史永久延长。再次调度前应读取新快照，而不是把昨天的工具结果当作长期有效的记忆。

模型输出不能直接当事实

验收应检查答案数字是否来自对应快照，以及算术是否正确。若模型写“最多调 14 辆”，工具返回的维修锁定和保留量已经反驳这个数。低温度或引用快照编号都不能自动修正这种计算错误，宿主可直接计算可调数量，把模型的职责收窄为解释。

动手验证

这组练习不发送模型请求。把前面的函数放进同一个 Python 文件，再增加固定响应适配器，就能检查消息序列和执行证据。

练习一：用离线回复走完两条路径

测试应真正调用被测试的函数，不能只定义一个假回复再打印通过。下面同时覆盖有工具和无工具两条出口。

组合练习：与本页前四段代码放在同一文件中运行
seen = []
def fake_model(messages, **options):
    seen.append([dict(m) for m in messages])
    if len(seen) == 1:
        return {"role": "assistant", "content": None, "tool_calls": [{
            "id": "call-qh-1", "type": "function", "function": {
                "name": "read_station", "arguments": '{"station_id":"QH-07"}'}}]}
    return {"role": "assistant", "content": "教学快照 sim-0730：可调 11 辆。"}

state = first_turn("QH-07 可调多少辆？", fake_model, [station_tool])
answer = finish_turn(state, fake_model, [station_tool])
assert [m["role"] for m in seen[1]] == ["system", "user", "assistant", "tool"]
assert seen[1][-1]["tool_call_id"] == "call-qh-1"
result = json.loads(seen[1][-1]["content"])
assert result["present"] - result["repair_locked"] - result["reserve"] == 11
assert "11" in answer
direct = first_turn("解释站点编码", lambda *a, **k: {
    "role": "assistant", "content": "编码用于定位站点。"}, [station_tool])
assert direct["status"] == "text" and len(direct["messages"]) == 3

再将参数改成 [] 或加入 tenant_id，应获得 bad_fields，且没有成功快照。把调用编号换成另一串字符，断言应随之失败，证明测试确实检查了配对关系。

练习二：亲手加一个工具

可以增加 dispatch_capacity，输入厢式车容量和已装车辆数，输出剩余装载空间。教学输入为容量 12、已装 5，预期剩余 7。工具只做减法并拒绝负数，不接真实车辆系统。先写独立函数与断言，再补声明和注册映射。

试着只加声明、不加处理器，观察模型请求可以构造出来但宿主拒绝执行；反过来只加处理器、不公开声明，模型通常不知道能力存在。两处都齐全以后，再比较模型是否选对工具。

观察日志时，只问这三个问题

读日志时分别核对：模型请求的名字和参数是否被接受；结果编号是否绑定到该请求；下一次请求是否真的携带这条结果。三个检查点分别对应接口、执行和反馈，任一点缺失都不宜宣布查询成功。练习日志只记录教学站点，不要把真实骑行人身份或访问凭证放进打印内容。

延伸对照：工具调用在真实生态里的形态

工具调用把模型输出接到程序执行入口。研究论文关心模型怎样学习选择工具，API 文档关心消息怎样传输，运行时则必须补足授权和失败处理。三个层次不宜混为一谈。

思想源头

Toolformer 研究如何让语言模型在生成中学习插入有用的 API 调用，ReAct 研究如何将行动与后续观察组织进连续求解过程。对自行车助手来说，学会选库存查询工具只是能力的一部分；是否允许读取某个区域、是否已经真正获得结果，仍需运行时保证。

本章结构化请求也不等同于研究里使用的原始文本协议。专门字段减少了字符串解析歧义，但输入校验、超时和证据检查并没有因此消失。

协议层：不同厂商，同一分工

在 OpenAI 风格协议中，调用常放在 assistant 的 tool_calls；Anthropic 采用 tool_use 和 tool_result 内容块。转换器需要保存调用标识、输入和错误语义，不能只重命名一个字段。多项请求、流式参数增量和中断后的恢复行为，都应单独写适配测试。

如果只用本地字典测试，能确认你的组装逻辑；要确认某个服务接受这种序列，还需在该服务支持的版本上做集成测试。本页没有执行这样的在线检查。

为什么会出现 MCP

站点查询可能由城市数据平台提供，维修工单由另一个系统维护。把每种客户端都嵌进一个进程，会让认证、版本和部署相互牵连。MCP 将工具发现与调用放到标准协议边界，宿主可以连接独立服务。

独立 server 不会替应用完成全部授权。工具目录可能展示某项能力，当前值班员仍未必有执行权限。工具描述和返回文本也应当视为外部数据，不能让它们修改宿主的安全政策。

本项目与生产实现的差距

链接中的最小工程重点是控制流，缺少完整的参数约束、取消传播、请求去重与审计保留策略。把它改成线上只读查询时，可以先给每次调用加请求编号和截止时间，再补权限拒绝测试。若以后引入“创建搬运任务”，还需要审批与幂等键，不能沿用只读函数的风险假设。

接口原文可查 OpenAI Function Calling、Anthropic Tool Use；协议边界见 MCP，研究方法见 Toolformer。

回顾与自测

一次库存回答的最小证据链是调用请求、校验结果、库存快照和最终表达。返回文本只是链末端的产物，缺少中间记录就无法追查错误数字来自哪里。

站点查询返回超时，能否继续回答 11 辆？

不能把教学快照的 11 辆冒充此次读取结果。允许陈述缓存时，也必须注明缓存来源和时间，否则应说明目前无法确认。

声明了工具，为什么仍然报 unknown_tool？

工具声明供模型选择，执行映射供宿主分发。两个表可能不同步。测试应比较公开名字和可执行名字，并检查当前权限是否允许访问。

第二次模型仍要求查询运力，怎样处理？

两轮版本应明确返回预算内未完成。需要多步决策时再改为有上限的循环，不要在收尾函数里隐式递归。
